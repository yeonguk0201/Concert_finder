# 관리자 등록·검수 안내

2026-10-06에 10/7 계획(W08/W09)을 선행 구현했다. 로컬 PostgreSQL·자동 테스트·모의 브라우저 검증을 완료했으며 원격 적용과 실제 관리자 계정 검증은 아직 하지 않았다.

## 적용

1. 기존 초기 마이그레이션이 적용된 프로젝트에서 [관리자 검수 마이그레이션](../supabase/migrations/202610070001_admin_review.sql)을 SQL Editor로 실행한다. 기존 데이터 백업·충돌 확인 후 적용하며 반복 실행용 SQL이 아니다.
2. Auth Users에서 관리자로 사용할 **기존 계정 UUID**를 확인한다. 브라우저에는 공개용 키만 사용하고 service role을 넣지 않는다.
3. SQL Editor에서 다음 템플릿의 UUID를 직접 교체해 권한을 등록한다. 일반 사용자가 이 테이블을 수정할 수 없고 마이그레이션이 자동으로 관리자를 지정하지 않는다.

```sql
insert into private.admins(user_id)
values ('여기에-기존-계정의-UUID')
on conflict(user_id) do nothing;
```

4. 해당 계정으로 앱에 로그인하고 **관리자 공연 검수**를 누른다. 직접 주소는 `/?page=admin`이다. 새 마이그레이션이 없으면 권한 확인 오류가 표시된다.

권한 해제는 SQL Editor에서 해당 계정의 `private.admins` 행을 삭제한다. 화면 버튼만으로 권한을 보호하지 않는다. 모든 RPC는 서버에서 관리자 여부를 재확인하며 일반 계정·비로그인은 조회/저장이 거부된다.

## 등록·검수·공개

- 밴드가 없다면 ‘밴드 등록’을 열어 공식 이름, 국가 코드, 쉼표로 구분한 검색 별칭을 입력한다. 밴드 목록은 일반 사용자에게 공개되므로 실제 밴드만 등록한다.
- ‘새 공연 등록’에서 초안으로 시작한다. 공연일·공식 발표일·장소·출연 밴드·출처·회차·일반 예매를 입력한다. 미정 날짜·시각·가격은 비워 둔다.
- 시각 입력은 브라우저 위치에 관계없이 KST로 해석한다. 날짜만 확인했다고 발표·예매 시각을 만들어 넣지 않는다.
- ‘검수 대기’로 저장한 후 출처 원문에서 정보를 확인한다. 출처별 ‘내용 확인 완료’와 ‘공식 출처에서 발표일을 확인했습니다’를 실제 확인 후 선택한다.
- 공개는 공연일·발표일·발표 확인·최소 한 확인된 공식 출처·출연 밴드를 요구한다. 실패 시 공연·출처·라인업·회차·예매·이력이 모두 이전 상태로 돌아간다.
- 공연 제목이나 목록 항목을 선택하면 수정할 수 있다. 다른 관리자의 수정이 있으면 덮어쓰기를 거부한다. 현재 입력을 별도로 보관한 뒤 ‘목록 다시 불러오기’와 공연 항목 선택으로 저장된 내용을 확인한다.
- 예매 수정 시 기존 예매 ID와 사용자의 저장을 유지한다. 오픈 시각 변경에만 예매 수정 번호가 증가한다. 최초 공개 시각은 수정·중단·재공개 후에도 보존된다.
- ‘공개 중단’은 일반 카탈로그에서 숨기고, ‘공식 취소 안내’는 취소 상태를 표시한다. 저장자는 공개 중단 이후에도 자신의 저장을 해제할 수 있다.

저장 직후 조회가 실패하면 ‘저장했지만 최신 목록을 확인하지 못했습니다’로 안내한다. 이때 재저장은 막고 목록을 다시 불러온 뒤 최신 수정 버전을 사용한다. 저장 자체의 실패와 구분한다.

변경 이력은 이 화면 RPC의 저장 전/후 내용을 관리자에게 보여준다. 최근 **전체 100건** 중 선택한 공연 기록을 표시하며, 기존 수동 SQL 등록이나 직접 테이블 변경의 모든 관련 테이블 이력을 소급해 만들지 않는다. 최초 스키마의 `private.concert_history`는 공연 행 변경을 별도로 보관한다. 출연일·출연 시각은 기존 라인업 행에 유지하지만 이 화면에서 편집하지 않는다. 푸시 발송·알림 대상 계산은 아직 없다.

## 실제 연결 검증

운영 카탈로그에 가상 공연을 공개하지 않는다. 실패 시나리오는 별도 테스트 프로젝트에서 실행한다.

- [ ] 관리자 계정에서 밴드·초안·출처·회차·예매 저장과 다시 조회를 확인한다.
- [ ] 비로그인과 일반 계정에서 초안/검수 대기 공연 및 관리자 이력이 보이지 않고 RPC 호출이 거부된다.
- [ ] 공식 검증이 완료된 실제 공연을 공개하고 별도 일반 브라우저의 새로고침으로 조회한다.
- [ ] 실제 공연의 시각 미정은 미정으로 유지되고 캘린더 다운로드가 비활성화된다.
- [ ] 두 관리자 창의 수정 충돌, 저장 실패·조회 실패 후 복구를 확인한다.
- [ ] 예매 시각 수정 후 저장 ID 유지·수정 번호·이력·최초 공개 시각을 확인한다.
- [ ] 공개 중단/취소와 기존 저장 해제를 확인한다.

DB 변경의 새로고침 없는 화면 반영은 W25에서 구현한다.

## 발표 날짜 검증과 저장 안내 · 2026-10-07

실제 사용자 입력에서 발표일(10/5)과 발표 시각의 한국 날짜(10/6)가 달라 초안 저장도 DB 제약으로 거부되는 것을 확인했다. 관리자 입력 화면은 두 날짜가 다르거나 발표 시각만 있고 발표일이 없을 때 구체적인 날짜·수정 안내를 저장 버튼 아래에 표시하고, 저장 요청을 보내지 않는다. 두 입력은 오류 상태와 안내를 연결한다. 미확인 시각은 비워 둘 수 있으며 UTC 날짜가 아니라 KST 날짜로 비교한다.

공연 저장 진행·성공·실패는 저장 버튼 바로 아래에서 확인한다. 저장은 성공했으나 목록 재조회가 실패하면 해당 위치의 `목록 다시 확인`으로 복구할 수 있다. 입력을 수정하면 이전 공연 저장 안내는 지운다. 밴드 등록 결과는 해당 등록 버튼 아래에 표시한다.

검증: 기존 테스트 중 37개 통과 후 새 테스트의 선택자 오류를 수정하고 관리자 5개 테스트를 재실행해 모두 통과(총 38개 검증). lint 경고 없음·build·diff 검사 통과. 로컬 모의 관리자 화면의 데스크톱/390px 모바일에서 날짜 오류·수정 후 성공 안내, 가로 넘침 없음·콘솔 오류 없음을 확인했다. 이 UI는 원격 배포 전이며 새로운 DB 마이그레이션은 필요하지 않다.
