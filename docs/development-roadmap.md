# encore. 개발 로드맵 및 상세 일정

작성일: 2026년 10월 6일 · 시간 기준: Asia/Seoul (KST)

**목표: 10월 12일 핵심 기능 구현, 10월 19일 베타 공개, 10월 26일 1차 완성.**

개발자가 종일 참여하고 AI가 구현·검증을 돕는 방식으로 기존 약 4일의 작업을 하루 목표로 묶는다. 하루에 연결된 기능 묶음을 구현하되 선행 조건과 실제 검증을 유지한다. 날짜는 공격적인 목표이며 완료 보장이 아니다. 10월 7일과 10월 12일에 실제 결과를 기준으로 조정한다. 외부 계정 설정·실제 기기 수신·사용자 피드백 대기는 구현 시간과 구분한다.

관련 문서: [베타 요구사항](product-requirements.md) · [기능별 작업 목록](development-backlog.md)

## 1. 제품 목표와 현재 상태

핵심 목표는 외부 공식 공연 정보를 자동으로 수집해 DB에 반영하고, DB 변경을 열린 앱 화면에 새로고침 없이 반영하는 것이다. 관리자는 수집 후보 검수·오류 수정·누락 보완을 담당하며 수동 등록만으로 핵심 기능 완료를 선언하지 않는다. 좋아하는 국내·해외 밴드가 한국에서 공연하면 소식을 전달한다. 단독 콘서트뿐 아니라 페스티벌 출연도 포함한다. 홈에는 찜한 밴드 소식과 찜하지 않은 밴드의 최근 내한 발표를 함께 보여준다.

### 완료된 작업

- [x] React + TypeScript + Vite 기반 반응형 웹앱 초안
- [x] 홈, 공연 탐색, 검색·지역·분류 필터, 공연 상세
- [x] 밴드 찜, 예매 일정 저장·삭제, 캘린더 다운로드
- [x] 브라우저 저장 유지 및 페스티벌 출연 밴드 매칭
- [x] 커밋·PR 템플릿, GitHub Actions 빌드·린트 검사
- [x] dev/main 브랜치 보호 및 첫 PR의 dev 병합

설정 없는 로컬 프리뷰는 가상 샘플과 브라우저 저장을 사용한다. 10/6에 Supabase 스키마·이메일 로그인·계정별 저장 코드를 구현하고 로컬 검증했다. 이후 실제 프로젝트의 환경변수·테이블·공개 카탈로그 조회·private 스키마 미노출 및 이메일 링크 요청 성공을 확인했고, 사용자가 실제 로그인·로그아웃 성공과 새로고침 후 로그인 상태 유지를 확인했다. 사용자가 A/B 밴드 찜 격리·일반 사용자 변경 제한·다른 브라우저/기기 찜 동기화를 확인했다. MCR 등록과 실제 예매 일정 저장 성공도 확인했다. 일정 유지·해제·격리·실패 복구의 실제 검증은 남아 있다. 이후 공식 출처 수집·DB 실시간 반영의 기본 흐름을 사용자가 확인했다. 10/9 알림 발송 코드를 구현·검증했고, 10/8 사용자가 노트북 웹·갤럭시·아이폰의 테스트 알림 수신·앱 열기·사이트를 닫은 상태의 수신을 확인했다. 10/9 사용자가 신규 공연·저장한 예매 알림·동의/기기 해제 차단과 Supabase 자동 발송의 실제 수신을 확인했다. W13~W16 구현·기본 전달은 완료했으며 상세 기기 시나리오와 지연 측정은 W17에서 이어간다. 공식 정보로 검증한 데이터만 실제 공연으로 공개하며, 샘플이 남아 있는 화면은 샘플 표시를 유지한다.

## 2. 첫 출시 범위

| 우선순위 | 기능 | 베타 완료 기준 |
| --- | --- | --- |
| 필수 | 회원가입·로그인·로그아웃 | 이메일 로그인 링크와 세션 유지, 실패 안내가 동작한다. 소셜 로그인은 후속으로 둔다. |
| 필수 | 밴드 찜·예매 일정 저장 | 계정별 서버 저장 및 다른 기기에서 동기화가 된다. |
| 필수 | 공연 탐색 | 신규 발표와 가까운 공연일을 구분하고 국내·내한·페스티벌 및 지역으로 찾을 수 있다. |
| 필수 | 공연 상세 | 공식 출처, 공연·예매 일시, 장소, 라인업, 예매 링크를 확인할 수 있다. 미발표 정보는 미정으로 표시한다. |
| 필수 | 관리자 검수·수정·보완 | 수집 후보의 출처·변경 내용을 검토해 공개하고 누락을 직접 등록한다. 일반 계정 변경은 차단한다. |
| 필수 | 신규 공연 알림 | 찜한 밴드의 공연 또는 페스티벌 출연 추가 시 수신 동의한 사용자에게 전달한다. |
| 필수 | 예매 전 알림 | 사용자가 저장한 일정에 대해 예매 1시간 전 알림을 제공한다. 시간 변경 및 저장 해제를 반영한다. |
| 필수 | 운영 기본 기능 | 오류 기록, 공개 환경, 계정·알림 설정 및 개인정보 처리 안내를 제공한다. |
| 필수 | 외부 공연 정보 자동 수집 | 최소 한 공식 출처에서 반복 실행 가능한 수집기로 신규·변경 후보를 수집하고 중복 없이 검수·공개 흐름에 연결한다. 실패·마지막 성공 시각·수집 주기를 기록한다. |
| 필수 | DB 변경의 화면 실시간 반영 | 공개된 신규 공연·수정·취소·찜·저장 변경을 새로고침 없이 반영한다. 재연결 시 재조회하고 사용자 전환 시 이전 구독을 해제한다. |
| 후속 | 변경·취소 알림 | 변경 이력을 남기고 관련 사용자에게 수정·취소 사실을 전달한다. |

앱스토어 출시, 동행·커뮤니티, 취소표 알림, 결제, 음악 스트리밍 서비스 연동, 전국 모든 공연의 자동 수집은 첫 출시 범위에서 제외한다.

알림 전달은 웹 푸시를 사용한다. 10월 8일 사용자가 노트북 웹·갤럭시 Chrome·아이폰 홈 화면 웹앱의 테스트 알림 수신, 알림 클릭 후 앱 열기, 사이트를 닫은 상태의 수신을 확인했다. 아이폰은 홈 화면 앱에서 이메일 인증번호로 로그인한다. 신규 공연/예매 알림의 실제 대상·시각과 정기 실행은 후속 검증한다. 이메일 대안은 미구현이다.

## 3. 주요 일정

| 단계 | 기간 | 결과물 | 단계 종료 기준 |
| --- | --- | --- | --- |
| 1주차: 핵심 기능 | 10/6~10/12 | DB·로그인·서버 저장·첫 자동 수집·실시간 반영·검수·알림·테스트 배포 | 공식 출처의 후보를 자동 수집하고 검수·공개하면 열린 앱에 반영되며, 찜한 사용자에게 알림을 전달하고 예매 일정을 저장할 수 있다. 실제 기기 검증까지 끝나야 기능 완료다. |
| 2주차: 베타 공개 | 10/13~10/19 | 5~10명 사용자 피드백, 오류 수정, 운영 안내, 공개 버전 | 계정·접근 권한·실제 정보·알림 검증 후 베타를 공개한다. |
| 3주차: 1차 완성 | 10/20~10/26 | 출처 수집 확장·검수 개선, 변경·취소 알림, 운영·회귀 검증, 포트폴리오 | 운영 가능한 버전을 공개하고 지원 범위·제약을 설명한다. |

최소 한 공식 출처의 자동 수집과 DB 변경의 화면 반영은 베타 공개의 선행 조건이다. 첫 출처의 API·접근 가능성·제공 범위를 먼저 확인한다. 외부 발표→수집→검수→DB 공개→화면 반영의 지연을 각각 기록한다. 외부 출처의 주기적 수집과 DB 실시간 구독을 구분하고, 미구현·미측정 상태에서 실시간 수집이나 속도를 약속하지 않는다. 빠른 구현에도 데이터 정확성·접근 권한·실제 알림 검증을 유지한다.

## 5. 하루 운영과 사용량 관리

하루에 기존 약 4일의 연결된 작업을 목표로 잡고 구현·검증·PR까지 묶어서 진행한다. 실제 기기 테스트·공식 정보 확인·코드 이해에 별도 시간을 둔다. 첫 주는 기능 구현을 집중하고 둘째 주에는 사용자 응답과 오류 수정을 흡수한다.

| 오후 초반 | 실제 사용·오류 재현, 핵심 시나리오 검증 |
| 오후 후반 | 수정·코드 리뷰·CI·PR 정리 |
| 마무리 | 구현 이유 이해, 결정사항·다음 작업 기록 |

AI 사용량은 작업 크기와 문맥 등에 따라 달라져 남은 한도를 개발 시간으로 환산하지 않는다. 기능 하나의 완료 기준을 명확히 하고 필요한 파일을 중심으로 작업한다. 한도가 부족하면 공연 출처 조사·정보 등록·직접 테스트·코드 학습을 진행한다. 진행 상태와 결정사항을 저장해 다음 작업에서 같은 조사를 반복하지 않도록 한다.

개발자는 범위·사용성·데이터 정확성을 판단하고 실제 기기로 확인한다. AI는 구현·검증·문서·PR 작성을 돕는다. 계정 연결이나 배포 설정처럼 필요한 사용자 작업이 있으면 일찍 준비한다.

## 6. 개발과 검증 규칙

- 최신 dev에서 작업 브랜치를 만들고 기능 단위로 PR을 작성한다.
- PR에는 변경 목적, 사용자 동작, 실제 검증 결과와 미검증 항목을 적는다.
- GitHub Actions의 Build and lint 검사 통과 후 dev에 병합한다.
- 공개 버전은 dev→main PR을 통해 반영한다. 병합과 배포는 각각 상태를 확인한다.
- 화면은 데스크톱과 모바일에서, 알림은 실제 기기에서 확인한다.
- 인증·계정별 데이터 접근·예약·중복 방지는 의미 있는 자동 검증을 추가한다.
- 필요한 환경변수 이름과 설정 방법을 문서화하고 비밀값은 Git에 넣지 않는다.
- 원격 DB 구조 변경은 마이그레이션으로 기록하고 되돌릴 방법을 고려한다.
