# encore. 개발 로드맵 및 상세 일정

작성일: 2026년 10월 6일 · 시간 기준: Asia/Seoul (KST)

**목표: 4주 안에 베타 공개(11월 2일), 6주 안에 1차 완성(11월 16일).**

개인 프로젝트로 종일 참여할 수 있는 상황을 전제로 한 계획이다. 날짜는 목표이며, 실제 데이터 확보와 알림 전달 검증 결과에 따라 조정한다. 첫 주 종료 시 실제 개발 속도를 확인해 남은 일정을 보정한다.

관련 문서: [베타 요구사항](product-requirements.md) · [기능별 작업 목록](development-backlog.md)

## 1. 제품 목표와 현재 상태

좋아하는 국내·해외 밴드가 한국에서 공연하면 소식을 전달한다. 단독 콘서트뿐 아니라 페스티벌 출연도 포함한다. 홈에는 찜한 밴드 소식과 찜하지 않은 밴드의 최근 내한 발표를 함께 보여준다.

### 완료된 작업

- [x] React + TypeScript + Vite 기반 반응형 웹앱 초안
- [x] 홈, 공연 탐색, 검색·지역·분류 필터, 공연 상세
- [x] 밴드 찜, 예매 일정 저장·삭제, 캘린더 다운로드
- [x] 브라우저 저장 유지 및 페스티벌 출연 밴드 매칭
- [x] 커밋·PR 템플릿, GitHub Actions 빌드·린트 검사
- [x] dev/main 브랜치 보호 및 첫 PR의 dev 병합

현재 공연 정보는 가상 샘플이며, 저장은 브라우저 내부에서만 이루어진다. 실제 로그인·서버 저장·공연 수집·푸시 발송은 아직 연결하지 않았다. 공식 정보로 검증한 데이터만 실제 공연으로 공개하며, 샘플이 남아 있는 화면은 샘플 표시를 유지한다.

## 2. 첫 출시 범위

| 우선순위 | 기능 | 베타 완료 기준 |
| --- | --- | --- |
| 필수 | 회원가입·로그인·로그아웃 | 이메일 로그인 링크와 세션 유지, 실패 안내가 동작한다. 소셜 로그인은 후속으로 둔다. |
| 필수 | 밴드 찜·예매 일정 저장 | 계정별 서버 저장 및 다른 기기에서 동기화가 된다. |
| 필수 | 공연 탐색 | 신규 발표와 가까운 공연일을 구분하고 국내·내한·페스티벌 및 지역으로 찾을 수 있다. |
| 필수 | 공연 상세 | 공식 출처, 공연·예매 일시, 장소, 라인업, 예매 링크를 확인할 수 있다. 미발표 정보는 미정으로 표시한다. |
| 필수 | 관리자 등록·수정 | 관리자만 데이터를 변경하고, 등록 내용을 검수한 후 공개한다. |
| 필수 | 신규 공연 알림 | 찜한 밴드의 공연 또는 페스티벌 출연 추가 시 수신 동의한 사용자에게 전달한다. |
| 필수 | 예매 전 알림 | 사용자가 저장한 일정에 대해 예매 1시간 전 알림을 제공한다. 시간 변경 및 저장 해제를 반영한다. |
| 필수 | 운영 기본 기능 | 오류 기록, 공개 환경, 계정·알림 설정 및 개인정보 처리 안내를 제공한다. |
| 후속 | 정보 수집 자동화 | 확보 가능한 공식 출처 1~2곳에서 후보 정보를 모으고 검수 후 공개한다. |
| 후속 | 변경·취소 알림 | 변경 이력을 남기고 관련 사용자에게 수정·취소 사실을 전달한다. |

앱스토어 출시, 동행·커뮤니티, 취소표 알림, 결제, 음악 스트리밍 서비스 연동, 전국 모든 공연의 자동 수집은 첫 출시 범위에서 제외한다.

알림은 웹 푸시를 우선 검증한다. 첫 주에 실제 휴대폰 수신 실험 후 지원 환경과 전달 방식을 확정한다. 어려운 환경에는 이메일 대안을 검증하고 지원 범위를 문서화한다. 전달이 구현되기 전에는 일정 저장을 알림 예약으로 표현하지 않는다.

## 5. 하루 운영과 사용량 관리

종일 참여가 가능해도 집중 개발은 하루 5~6시간을 기준으로 삼고, 나머지는 테스트·학습·데이터 조사·휴식에 사용한다. 일요일은 여유일로 두어 지연을 흡수한다.

| 구간 | 주된 작업 |
| --- | --- |
| 오전 | 당일 완료 기준 확인, 기능 하나 설계·구현 |
| 오후 초반 | 실제 사용·오류 재현, 핵심 시나리오 검증 |
| 오후 후반 | 수정·코드 리뷰·CI·PR 정리 |
| 마무리 | 구현 이유 이해, 결정사항·다음 작업 기록 |

AI 사용량은 작업 크기와 문맥 등에 따라 달라져 남은 한도를 개발 시간으로 환산하지 않는다. 기능 하나의 완료 기준을 명확히 하고 필요한 파일을 중심으로 작업한다. 한도가 부족하면 공연 출처 조사·정보 등록·직접 테스트·코드 학습을 진행한다. 진행 상태와 결정사항을 저장해 다음 작업에서 같은 조사를 반복하지 않도록 한다.

개발자는 범위·사용성·데이터 정확성을 판단하고 실제 기기로 확인한다. AI는 구현·검증·문서·PR 작성을 돕는다. 계정 연결이나 배포 설정처럼 필요한 사용자 작업이 있으면 일찍 준비한다.

## 6. 개발과 검증 규칙

- 최신 dev에서 작업 브랜치를 만들고 기능 단위로 PR을 작성한다.
- PR에는 변경 목적, 사용자 동작, 실제 검증 결과와 미검증 항목을 적는다.
- GitHub Actions의 Build and lint 검사 통과 후 dev에 병합한다.
- 공개 버전은 dev→main PR을 통해 반영한다. 병합과 배포는 각각 상태를 확인한다.
- 화면은 데스크톱과 모바일에서, 알림은 실제 기기에서 확인한다.
- 인증·계정별 데이터 접근·예약·중복 방지는 의미 있는 자동 검증을 추가한다.
- 필요한 환경변수 이름과 설정 방법을 문서화하고 비밀값은 Git에 넣지 않는다.
- 원격 DB 구조 변경은 마이그레이션으로 기록하고 되돌릴 방법을 고려한다.

| AI 한도 또는 외부 설정 대기 | 매일 | 독립적인 조사·테스트·학습을 진행하고 다음 구현을 위한 재현 자료를 준비한다. |

날짜가 밀리면 필수 흐름을 축소하기보다 후속 기능과 지원 범위를 줄인다. 완성 날짜보다 정확한 정보와 동작 검증을 우선한다.
