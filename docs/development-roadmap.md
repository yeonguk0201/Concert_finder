### 10/12 추가 작업 · 주요 아티스트 DB 관리 (실제 사전 등록·사진 교체 검증)

- 국내 록·해외 록·J-pop 주요 아티스트를 검증한 MusicBrainz ID로 사전 등록하고 한국어·영문·일본어 별칭을 관리한다. 같은 외부 ID는 기존 등록을 재사용하고 동명이인은 이름만으로 합치지 않는다. 공연이 없어도 검색·찜할 수 있게 유지한다.
- 일반 검색은 DB 결과를 먼저 제공하고 외부 검색으로 누락을 보완한다. DB/외부 중복 결과를 정리하고 Ado·한국어 별칭·미등록 아티스트를 기준으로 정확도와 응답 시간을 검증한다.
- 대표 이미지의 관리자 지정·교체·삭제와 DB 이미지 우선 표시를 구현한다. 이미지 URL뿐 아니라 원본 출처·저작자·라이선스/이용 근거를 보관하고, 이미지가 없거나 실패하면 이니셜로 표시한다. Ado처럼 자동 연결 사진이 없는 주요 아티스트도 검증한 이미지를 지정할 수 있게 한다.
- 완료 기준: 사전 등록을 다시 실행해도 중복이 없고, 일반 사용자의 카탈로그/이미지 수정은 차단되며, 이미지 지정·교체·실패와 모바일 카드 표시를 확인한다. 10/12에 실제 MBID를 확인한 20팀의 등록 manifest·반복 등록 RPC·DB 우선 검색/외부 중복 제거·대표 이미지 직접 관리를 로컬 구현·검증했다. 이후 사용자 요청으로 운영 DB의 20팀을 등록/재사용했다(신규 12·기존 8, 전체 54팀). 6팀 신원 보류를 공식 근거로 수동 검수했고 재실행 중복 없음·기존 관계 보존, Ado/아도 검색, Radiohead 실제 사진 지정·교체·새로고침과 모바일 표시를 확인했다. [실행 결과·남은 점검](artist-management-20261012.md).

10/12 구현 진행: W26 출처별 임대·시작/종료·제한 재시도·운영 상태와 매시간 workflow, W27 서버 조건부 공개·중복/예외 검수·초기 채움 무알림을 로컬 구현했다. 현재 파서는 공식 발표 등 필수 근거가 부족해 현 후보의 자동 공개는 보류된다. 실제 DB의 운영 상태 조회는 확인했으며 실제 무인 공개·배포·24시간 관측은 남아 있다. [자동 운영 구현과 제한](automated-catalog-20261012.md).

## 1. 제품 목표와 현재 상태

핵심 목표는 국내 록·해외 록·J-pop 밴드/록 성향 아티스트의 한국 공연을 여러 공식 출처에서 매시간 수집하고, 검증 조건을 충족하면 자동 공개해 열린 앱에 반영하는 것이다. 관리자는 불확실한 후보·출처 충돌·중요 변경의 예외 검수와 정정·누락 보완을 담당한다. 수동 등록이 데이터 확보의 기본 경로가 되어서는 안 된다. 단독 콘서트와 록 페스티벌·혼합 페스티벌의 대상 밴드 출연을 포함하고 일반 팝·재즈·클래식 전체로 범위를 넓히지 않는다. 홈에는 찜한 밴드 소식과 대상 장르의 최근 국내/내한 소식을 제공한다. 국적과 장르를 별도로 판정한다.

## 5. 하루 운영과 사용량 관리

하루에 기존 약 4일의 연결된 작업을 목표로 잡고 구현·검증·PR까지 묶어서 진행한다. 실제 기기 테스트·공식 정보 확인·코드 이해에 별도 시간을 둔다. 첫 주는 기능 구현을 집중하고 둘째 주에는 사용자 응답과 오류 수정을 흡수한다.

| 구간 | 주된 작업 |
| --- | --- |
| 오전 | 당일 기능 묶음의 완료 기준 확인, 선행 작업부터 설계·구현 |
| 오후 초반 | 실제 사용·오류 재현, 핵심 시나리오 검증 |
| 오후 후반 | 수정·코드 리뷰·CI·PR 정리 |
| 마무리 | 구현 이유 이해, 결정사항·다음 작업 기록 |

AI 사용량은 작업 크기와 문맥 등에 따라 달라져 남은 한도를 개발 시간으로 환산하지 않는다. 기능 하나의 완료 기준을 명확히 하고 필요한 파일을 중심으로 작업한다. 한도가 부족하면 공연 출처 조사·정보 등록·직접 테스트·코드 학습을 진행한다. 진행 상태와 결정사항을 저장해 다음 작업에서 같은 조사를 반복하지 않도록 한다.

개발자는 범위·사용성·데이터 정확성을 판단하고 실제 기기로 확인한다. AI는 구현·검증·문서·PR 작성을 돕는다. 계정 연결이나 배포 설정처럼 필요한 사용자 작업이 있으면 일찍 준비한다.

## 6. 개발과 검증 규칙

- 최신 dev에서 작업 브랜치를 만들고 기능 단위로 PR을 작성한다.
- PR에는 변경 목적, 사용자 동작, 실제 검증 결과와 미검증 항목을 적는다.
- GitHub Actions의 Build and lint 검사 통과 후 dev에 병합한다.
- 공개 버전은 dev→main PR을 통해 반영한다. 병합과 배포는 각각 상태를 확인한다.
- 화면은 데스크톱과 모바일에서, 알림은 실제 기기에서 확인한다.
- 인증·계정별 데이터 접근·예약·중복 방지는 의미 있는 자동 검증을 추가한다.
- 필요한 환경변수 이름과 설정 방법을 문서화하고 비밀값은 Git에 넣지 않는다.
- 원격 DB 구조 변경은 마이그레이션으로 기록하고 되돌릴 방법을 고려한다.
