# 중복·취소·수동 차단과 무알림 초기 공개 검증 — 2026-10-30

후속 실제 운영 조회: [실제 후보 최종 상태 확인과 재개 기준](publication-live-state-check.md). 아래의 가상 검증과 실제 운영 readback을 구분한다.

[공개 실행기 보완](publication-executor.md) 후속 검증이다. 운영 공개 ON·운영 SQL 적용·실제 발송을 실행하지 않고, 기존 SQL 제안을 인메모리 PGlite에서 실행했다. 실제 운영 후보의 최종 상태 확인은 다음 단계다.

## 검증 방법

`tests/publication-executor.test.mjs`에서 기존 ingestion·공개·알림 DB 함수를 함께 실행한다. 가상 아티스트를 승인하고, 해당 아티스트를 찜한 가상 사용자에 알림 동의와 활성 기기를 부여한다. 초기 공개 검증을 위해 **격리 DB의 가상 정책만** 켠다. 실제 서버·API·발송기와는 연결하지 않는다. 각 사례는 transaction rollback으로 격리한다.

단순히 공개 0건만 확인하지 않고, 정상 신규 후보는 실제 공개 행·회차·예매 행과 최초 공개 이력이 생기는지, 익명 사용자에게 조회되는지, 알림 워커가 가져갈 항목이 있는지까지 확인한다. live 정상 사례는 알림 delivery 1건이 생성되는 양성 대조로 사용한다.

## 결과와 한계

실행기 검사 **37개(상위 테스트 포함)** 통과. 추가 경계 사례 10개와 배치 중복의 원자성 검증을 강화했다. 이번 검증에서 실행기 SQL·앱 동작 코드는 추가 수정하지 않았다.

관련 Node 회귀 **98개 전부 통과**(실패·skip 0): 실행기·준비 자문·pilot·기존 자동 공개·아티스트 검수·worker 권한·예약 수집·KOPIS·Reissue/NOL·알림 DB/worker/Cron/edge 검사다. `npm run lint`, `git diff --check` 통과. 앱 코드와 SQL이 이전 통과 시점 이후 바뀌지 않아 build는 앞 단계 통과 결과를 재사용한다(기존 500kB 번들 경고 유지).

이 결과는 가상 데이터에 대한 **로컬 통합 검증**이다. 실제 PostgreSQL의 여러 연결 간 동시 실행·네트워크 응답 유실·운영 RLS 설정·실제 동의/기기의 최종 발송을 검증했다고 확대하지 않는다. 수집 후보의 취소 신호는 검토로 보내며 실제 공연을 자동 취소하는 구현은 아니다. 실제 후보 readback과 운영 적용 호환성 확인은 남아 있고, **공개 ON은 별도 승인 후 실행한다.**
