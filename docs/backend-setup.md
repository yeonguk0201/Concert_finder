# Supabase 연결과 검증

실제 데이터는 Supabase에 저장하고 가상 샘플은 `src/data.ts`와 기존 브라우저 저장에만 둔다. `.env` 두 값이 모두 비어 있으면 기존 로컬 프리뷰, 연결 설정이 있으면 계정 모드다. 설정 오류나 서버 장애 때 샘플을 실데이터처럼 대신 표시하지 않는다.

## 신규 프로젝트 준비

1. Supabase SQL Editor에서 `supabase/migrations/202610060001_initial.sql`을 실행한다. 기존 테이블이 있는 프로젝트에는 바로 실행하지 말고 구조와 충돌을 확인한다. 마이그레이션은 한 번만 적용한다.
2. `.env.example`을 `.env`로 복사하고 프로젝트 상단 Connect 창에서 Project URL과 공개용 publishable key를 확인해 넣는다. service_role·secret key와 DB 비밀번호는 브라우저 코드나 `VITE_` 변수에 넣지 않는다.
3. Auth → URL Configuration에서 Site URL에 `http://localhost:5173`, Redirect URLs에 `http://localhost:5173/**`를 등록한다. `127.0.0.1`로 접속한다면 그 주소도 별도로 등록한다. 링크 요청에 원래 화면을 보존하는 query가 포함되므로 개발용 경로 허용을 확인한다. 배포 후에는 실제 HTTPS 복귀 경로를 명시적으로 등록하고 광범위한 wildcard는 개발 환경에만 사용한다.
4. 이메일 provider와 이메일 템플릿을 확인한다. 기본 magic link 템플릿을 사용한다. SPA는 implicit flow로 링크를 연 브라우저에서 세션을 받는다. 외부 기기에서도 로그인할 수 있으나 원래 기기의 세션을 자동 생성하지 않는다.
5. 개발 서버를 다시 시작한다. 실제 밴드·공연 데이터가 없으면 빈 목록이 정상이다. 샘플을 운영 DB에 넣지 않는다.

관리자는 SQL Editor에서 `private.admins`에 검증한 Auth 사용자 UUID를 직접 추가한다. 일반 클라이언트에는 이 테이블의 읽기·쓰기 권한이 없고 사용자 설정으로 승격할 수 없다. 관리자 화면은 W08 후속 작업이다.

## 데이터 구조

밴드는 UUID·공식 이름·별칭·국적을 가진다. 이름은 중복 가능하다. 공연 형식(solo/festival)과 밴드 국적은 독립적이다. 공연 기간은 date, 정확한 공연 회차·출연 시각·일반 예매 시각은 timestamptz로 저장한다. 날짜만 확인한 항목에는 시간을 만들지 않는다. 미정은 NULL이다.

공연·출처·회차·라인업·일반 예매를 분리한다. 일반 예매는 공연당 하나다. 예매 시각 변경 시 revision이 증가한다. 공개에는 공연 날짜, 발표 날짜와 확인 결과, 확인한 HTTPS 공식 출처, 라인업이 필요하다. 최초 공개 시각은 수정·재공개에도 유지하며 공연 수정 전 값을 비공개 이력에 남긴다. 공개 변경과 기기별 발송 중복 식별 구조는 준비했으나 알림 생성·발송 worker는 아직 구현하지 않았다.

찜·저장·알림 설정은 auth.users의 소유자 UUID를 사용하고 계정 삭제 시 cascade로 정리한다. 알림 동의 기본값은 false다. RLS로 본인 행만 읽고 변경한다. 공개 전 공연과 관련 테이블은 방문자에게 숨기고 카탈로그 변경은 관리자만 허용한다. 공개 중단한 공연의 저장 행은 사용자가 삭제할 수 있다.

## 로컬 자동 검증

`npm test`는 PGlite의 실제 PostgreSQL 엔진에 테스트용 auth 스키마와 역할을 만들고 마이그레이션을 실행한다. 빈 프로젝트부터 생성·공개 조건·관리자 제한·A/B 사용자 격리·대리 저장 차단·취소 공연 저장 차단·삭제 cascade를 검증한다. 테스트용 이메일·밴드·공연은 메모리에만 생성한다.

이 검증은 Supabase의 실제 JWT 발급, 이메일 전달, 원격 PostgREST 설정과 기기 동기화를 대체하지 않는다. 실제 연결 후 A01/A02/F01/F02를 직접 실행하고 결과를 기록한다.

- [ ] 원격 마이그레이션 실행 및 RLS 확인

프로젝트가 비어 있어 비로그인 계정 테이블 조회의 빈 결과만으로 소유권 격리를 입증하지 않는다. private 스키마 미노출과 사용자별 행 접근 차단도 서로 다른 검증이다. 이메일 요청 성공을 실제 수신·로그인·세션 복구 완료로 표시하지 않는다. `.env` 값과 인증 토큰은 검증 기록에 남기지 않는다.

## 적용과 복구

초기 마이그레이션은 신규 프로젝트용이다. 운영 적용 전에 백업을 확보한다. 실패하면 트랜잭션을 롤백하고 원인을 해결한 뒤 다시 실행한다. 적용 후 데이터가 존재하면 테이블을 삭제해 되돌리지 말고 후속 수정 마이그레이션을 만든다. 개발용 빈 프로젝트만 초기화할 수 있다.
