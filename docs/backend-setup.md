# Supabase 연결과 검증

실제 데이터는 Supabase에 저장하고 가상 샘플은 `src/data.ts`와 기존 브라우저 저장에만 둔다. `.env` 두 값이 모두 비어 있으면 기존 로컬 프리뷰, 연결 설정이 있으면 계정 모드다. 설정 오류나 서버 장애 때 샘플을 실데이터처럼 대신 표시하지 않는다.

## 신규 프로젝트 준비

1. Supabase SQL Editor에서 `supabase/migrations/202610060001_initial.sql`을 실행한다. 기존 테이블이 있는 프로젝트에는 바로 실행하지 말고 구조와 충돌을 확인한다. 마이그레이션은 한 번만 적용한다.
2. `.env.example`을 `.env`로 복사하고 프로젝트 상단 Connect 창에서 Project URL과 공개용 publishable key를 확인해 넣는다. service_role·secret key와 DB 비밀번호는 브라우저 코드나 `VITE_` 변수에 넣지 않는다.
3. Auth → URL Configuration에서 Site URL에 `http://localhost:5173`, Redirect URLs에 `http://localhost:5173/**`를 등록한다. `127.0.0.1`로 접속한다면 그 주소도 별도로 등록한다. 링크 요청에 원래 화면을 보존하는 query가 포함되므로 개발용 경로 허용을 확인한다. 배포 후에는 실제 HTTPS 복귀 경로를 명시적으로 등록하고 광범위한 wildcard는 개발 환경에만 사용한다.
4. 이메일 provider와 이메일 템플릿을 확인한다. 기본 magic link 템플릿을 사용한다. SPA는 implicit flow로 링크를 연 브라우저에서 세션을 받는다. 외부 기기에서도 로그인할 수 있으나 원래 기기의 세션을 자동 생성하지 않는다.
5. 개발 서버를 다시 시작한다. 실제 밴드·공연 데이터가 없으면 빈 목록이 정상이다. 샘플을 운영 DB에 넣지 않는다.

관리자는 SQL Editor에서 `private.admins`에 검증한 Auth 사용자 UUID를 직접 추가한다. 일반 클라이언트에는 이 테이블의 읽기·쓰기 권한이 없고 사용자 설정으로 승격할 수 없다. 관리자 화면은 W08 후속 작업이다.

## 데이터 구조

밴드는 UUID·공식 이름·별칭·국적을 가진다. 이름은 중복 가능하다. 공연 형식(solo/festival)과 밴드 국적은 독립적이다. 공연 기간은 date, 정확한 공연 회차·출연 시각·일반 예매 시각은 timestamptz로 저장한다. 날짜만 확인한 항목에는 시간을 만들지 않는다. 미정은 NULL이다.

공연·출처·회차·라인업·일반 예매를 분리한다. 일반 예매는 공연당 하나다. 예매 시각 변경 시 revision이 증가한다. 공개에는 공연 날짜, 발표 날짜와 확인 결과, 확인한 HTTPS 공식 출처, 라인업이 필요하다. 최초 공개 시각은 수정·재공개에도 유지하며 공연 수정 전 값을 비공개 이력에 남긴다. 공개 변경과 기기별 발송 중복 식별 구조는 준비했으나 알림 생성·발송 worker는 아직 구현하지 않았다.

찜·저장·알림 설정은 auth.users의 소유자 UUID를 사용하고 계정 삭제 시 cascade로 정리한다. 알림 동의 기본값은 false다. RLS로 본인 행만 읽고 변경한다. 공개 전 공연과 관련 테이블은 방문자에게 숨기고 카탈로그 변경은 관리자만 허용한다. 공개 중단한 공연의 저장 행은 사용자가 삭제할 수 있다.

## 로컬 자동 검증

`npm test`는 PGlite의 실제 PostgreSQL 엔진에 테스트용 auth 스키마와 역할을 만들고 마이그레이션을 실행한다. 빈 프로젝트부터 생성·공개 조건·관리자 제한·A/B 사용자 격리·대리 저장 차단·취소 공연 저장 차단·삭제 cascade를 검증한다. 테스트용 이메일·밴드·공연은 메모리에만 생성한다.

이 검증은 Supabase의 실제 JWT 발급, 이메일 전달, 원격 PostgREST 설정과 기기 동기화를 대체하지 않는다. 실제 연결 후 A01/A02/F01/F02를 직접 실행하고 결과를 기록한다.

## 실제 연결 체크리스트

### 밴드 찜과 관리자 변경 제한을 직접 확인하기

2026-10-06 조회에서 원격 `bands`는 0개였다. 계정 모드는 샘플 밴드를 사용하지 않는다. 상단 검색은 이제 공연 유무와 관계없이 등록된 밴드 이름·별칭도 찾는다. 밴드 관리 화면에서는 검색 중에도 해당 화면을 유지한다.

1. SQL Editor에서 [Oasis 등록 SQL](../supabase/manual/register-oasis.sql)을 실행한다. [공식 사이트](https://oasisinet.com/the-story/)로 확인한 실제 밴드 이름과 별칭만 등록한다. 공연·예매 일정은 생성하지 않으며 같은 SQL을 재실행해도 지정 UUID의 행을 덮어쓰지 않는다.
2. 앱을 새로고침하고 `Oasis` 또는 `오아시스`를 검색한다. 계정 A로 찜하고 새로고침 후 찜 상태가 유지되는지 확인한다.
3. 로그아웃 후 다른 이메일의 계정 B로 로그인한다. Oasis 밴드 자체는 누구에게나 보이지만 B의 버튼은 `찜하기`여야 한다. B에서 찜했다가 해제한 뒤 A로 돌아와 A의 찜은 유지되는지 확인한다. 같은 계정을 다른 브라우저에서 여는 것은 A/B 격리 검증이 아니다.
4. 일반 사용자 계정이 한 개 이상 있으면 SQL Editor에서 [일반 사용자 변경 차단 SQL](../supabase/manual/verify-catalog-rls.sql) **전체**를 실행한다. 정상 결과는 `PASS: non-admin ...`이며 오류가 없어야 한다. SQL Editor가 결과 행을 표시하지 않으면 실행 로그에서 SELECT 결과를 확인한다. 단순히 Table Editor/SQL Editor로 데이터를 수정하는 것은 관리자 제한 검증이 아니다. 이 파일은 실제 일반 사용자의 UUID와 `authenticated` 역할을 설정해 밴드·공연의 추가/수정/삭제와 자기 관리자 승격이 차단되는지 검사한다. UPDATE/DELETE의 0행 처리도 정상적인 RLS 차단이다.
5. 검증용 행은 마지막 `ROLLBACK`으로 제거된다. 오류가 발생하면 `ROLLBACK;`을 별도로 실행한 뒤 오류를 확인한다. 관리자를 추가하거나 실제 찜을 지우지 않는다. 이 검사는 DB 정책을 확인하며 실제 JWT 발급·브라우저 저장 요청의 검증을 대신하지 않는다.

두 SQL은 로컬 PostgreSQL 테스트에서 실행했고, 잘못 열린 INSERT 정책에서는 차단 검사가 실패하는 것도 확인했다. 2026-10-06 사용자가 밴드 등록, A/B 계정 찜·새로고침 유지·상호 변경 격리, 원격 차단 SQL 검증을 모두 완료했다고 보고했다. 차단 SQL은 SQL Editor의 `Run without RLS`로 실행했으나 내부 `SET LOCAL ROLE authenticated`와 일반 사용자 UUID 설정으로 실제 검증 구간의 권한을 제한한다. 전체 스크립트가 오류 없이 PASS에 도달했을 때에만 차단 검증 성공으로 해석한다. 단순 실행 성공만으로 이를 대체하지 않는다. 근거: [PostgreSQL SET ROLE](https://www.postgresql.org/docs/current/sql-set-role.html). 실제 공연 저장·다기기 일정 검증은 공개된 공식 공연 및 예매 데이터가 필요하다. 관리자 계정의 정상 편집은 로컬 정책 테스트에서 확인했으며 원격 관리자 편집 화면은 W08 범위다.

## 적용과 복구

### MCR 실제 공연으로 일정 저장 검증하기

2026-10-06 원격 공개 조회에서 MCR 일반 예매 행과 2025-07-14 12:00 KST 시각이 존재함을 확인했다. `ticket_schedules.concert_id`가 UNIQUE인 일대일 관계라 PostgREST가 객체로 반환하지만 앱은 배열로 읽어 미정 표시와 저장 비활성화가 발생했다. 객체·배열·NULL 응답을 처리하도록 수정했다. 일대일 응답과 미정 시각의 저장 회귀 테스트를 포함한 21개 테스트·lint/build를 확인했다. 실제 카탈로그 화면의 예매 시각·가격·링크 및 활성화된 저장 버튼을 확인했으며, 이후 사용자가 로그인 계정의 실제 저장 성공을 확인했다. 새로고침·해제·다기기 일정 유지와 일정 A/B 격리는 확인 대기다.

[MCR 밴드·공연 등록 SQL](../supabase/manual/register-mcr-korea-2026.sql) 전체를 SQL Editor의 postgres 역할로 실행한다. 밴드, 공연, 공식 출처, 회차·라인업, 일반 예매를 한 트랜잭션에서 등록한 뒤 공개한다. 일반 사용자 앱에는 카탈로그 등록 권한이 없다. 원격 등록은 사용자가 실행한 후 확인한다.

2026-10-06 확인한 [주최사 안내](https://ualive.com/concerts/397)는 2026-11-07 19:00 인천 파라다이스시티 컬처파크다. [연기 공지](https://www.ticketlink.co.kr/global/en/help/notice/63744)에 따라 기존 4월 공연을 11월 일정으로 등록한다. 앱 새로고침 후 `MCR`, `마이케미컬로맨스` 또는 영문 이름으로 검색한다. 공연 상세에서 `예매 일정 저장`을 누르고 `내 예매 일정` → 새로고침 → 다른 브라우저의 같은 계정에서 유지되는지 확인한다. 다른 계정에는 저장되지 않아야 하고, 저장 해제 후 다시 불러오면 제거돼야 한다. SQL 재실행은 기존 행과 저장을 유지하며 예매 revision·최초 공개 시각을 변경하지 않는다. 추후 공식 일정 변경은 별도 검토 후 수정한다. 이미 지난 일반 예매 오픈일의 저장 기능 검증이며, 실제 티켓 구매나 새로운 예매 오픈·푸시 발송을 의미하지 않는다.

초기 마이그레이션은 신규 프로젝트용이다. 운영 적용 전에 백업을 확보한다. 실패하면 트랜잭션을 롤백하고 원인을 해결한 뒤 다시 실행한다. 적용 후 데이터가 존재하면 테이블을 삭제해 되돌리지 말고 후속 수정 마이그레이션을 만든다. 개발용 빈 프로젝트만 초기화할 수 있다.

## 로그인 오류 점검 · 2026-10-06

사용자가 재사용/만료 링크에서 안내가 나타나지 않고 로그아웃 후 링크 재요청이 실패한다고 보고했다.

- 링크 안내 누락: StrictMode의 effect 재실행 중 첫 실행이 URL 오류를 지운 뒤 예약한 상태 변경이 취소됐다. 오류를 초기 상태에서 읽도록 수정했고 query·fragment의 error/error_code/error_description 및 같은 페이지 hash 이동을 처리한다. 원래 page/event는 보존하며 서버 설명 원문은 표시하지 않는다. StrictMode 회귀 테스트와 데스크톱·390px 모바일의 모의 otp_expired 복귀 화면으로 검증했다. 실제 재사용/만료 이메일 링크의 재검증은 아직 남아 있다.
- 재요청 실패: 실제 프로젝트에서 HTTP 429, over_email_send_rate_limit을 확인했다. 앱에서도 이메일 발송 한도 안내가 표시됨을 확인했다. 로그아웃 이후 로컬 상태 오류로 단정하지 않는다. 한도 초과·짧은 재요청 간격·요청량 제한·네트워크·서버 오류를 구분해 안내한다.
- 기본 이메일 provider는 프로젝트당 시간당 2통이며 동일 이메일의 기본 재요청 간격은 60초다. 실제 발송 제한은 provider와 프로젝트 설정에 따른다. 총량 한도 초과를 60초 대기만으로 해결한다고 안내하지 않는다. 제한 해제 후 재시도하거나 반복 검증·베타 준비 시 별도 SMTP 연결을 준비한다. 이번 수정에서 외부 서비스 생성·SMTP 변경·인증 제한 변경은 하지 않았다.
- 검증: 총 17개 자동 테스트(1개 PostgreSQL 통합, 16개 프런트엔드), lint/build, diff check 통과. 발송 한도 상태에서 정상 새 링크 발송·로그인 복구는 아직 재검증하지 않았다.

공식 문서: [인증 요청·이메일 발송 제한](https://supabase.com/docs/guides/auth/rate-limits), [인증 오류 코드](https://supabase.com/docs/guides/auth/debugging/error-codes).

## 저장 실패·복구 검증 · 2026-10-06

`tests/account-flow.test.tsx`는 실제 Supabase SDK와 accountApi·useAccountStorage를 실행하고 HTTP 전송(fetch) 계층에서 TypeError를 주입한다. 테스트 주소는 example.test이고 원격 네트워크 요청이나 실제 사용자 데이터 변경은 없다. 정상 전송은 메모리 응답으로 재현하며 저장·삭제 실패 시 기존 상태, 중복 없는 재시도, 조회 실패 시 쓰기 차단과 복구를 확인한다. `tests/app.test.tsx`는 실패 안내와 성공 오표시 방지·재시도 화면을 검증한다. 총 23개 테스트(1개 PostgreSQL 통합, 22개 프런트엔드), lint/build·diff check 통과. 실제 Supabase 서버 장애·실제 로그인 브라우저의 오프라인 전환은 이 결과로 완료 표시하지 않는다.
