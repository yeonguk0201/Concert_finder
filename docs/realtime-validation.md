# DB 변경 반영과 실제 연결 검증

10/8 계획을 2026-10-07에 구현했다. 원격 공개 키로 `catalog_signal`·`account_signals` 조회가 404여서 마이그레이션 적용과 실제 두 브라우저 검증은 대기다.

## 구조와 적용

기존 초기·관리자 마이그레이션 다음에 `202610080002_realtime.sql`을 실행한다. 두 신호 테이블만 `supabase_realtime` publication에 추가한다. [Supabase Postgres Changes 문서](https://supabase.com/docs/guides/realtime/postgres-changes)의 publication·RLS 기반 구독을 사용한다.

공개 신호는 카탈로그 수정 번호만 전달한다. 공개 공연과 관계 정보·밴드 변경 때 갱신하고, 초안 공연 수정은 공개 신호를 만들지 않는다. 공개 중단·삭제도 신호를 보내므로 기존 공개 행이 RLS로 보이지 않게 된 후에도 화면에서 제거된다. 계정 신호는 본인 UUID와 수정 번호만 본인 RLS로 읽는다. 원본 저장 테이블의 DELETE 데이터를 방송하지 않는다. 계정 삭제는 신호를 cascade 제거한다.

클라이언트는 신호를 받은 뒤 기존 RLS 조회로 전체 목록을 다시 읽는다. 150ms 동안 연속 변경을 합친다. 구독 성공·재연결·온라인 복귀·화면 복귀 때 재조회하며 30초 간격 조회로 누락을 복구한다. 저장 중 받은 신호는 쓰기 완료 뒤 처리한다. 계정 전환·로그아웃 때 구독과 대기 타이머를 제거하고 이전 계정의 늦은 응답을 무시한다. 오류 시 기존 목록을 보존하고 재시도를 안내한다.

`실시간 연결됨`은 WebSocket 구독 성공 상태다. publication이 빠진 경우에도 연결은 성공할 수 있으므로 실제 행 변경 검증을 대신하지 않는다. 알림·푸시 전달과도 별개다.

## 원격 확인 절차

1. SQL 적용 후 아래 조회에서 두 신호 테이블이 등록되었는지 확인한다.

```sql
select schemaname, tablename from pg_publication_tables
where pubname = 'supabase_realtime'
  and tablename in ('catalog_signal', 'account_signals');
```

2. 새 앱 빌드를 실행/배포하고 관리자 A와 일반 사용자 B의 두 브라우저를 연다. 실제 공식 정보만 검수해 공개한다. B가 새로고침 없이 목록·상세·검색에서 확인하는지 측정한다. 공개 중단·라인업·회차·예매 수정도 반복한다.
3. 같은 계정의 두 브라우저에서 찜·저장·삭제를 서로 확인한다. 계정 B로 전환한 브라우저에서는 A의 목록을 보지 않아야 한다. 비로그인에는 계정 신호가 보여서는 안 된다.
4. 한 브라우저를 오프라인으로 두고 다른 브라우저에서 수정한 뒤 온라인 복귀·백그라운드 복귀 후 최신 상태를 확인한다. 저장 처리 중 원격 변경도 확인한다.
5. 관리자 저장 완료→다른 브라우저 갱신의 시간을 기록한다. WebSocket 경로와 30초 복구 조회 경로를 구분한다. 변경한 데이터는 공식 내용을 유지한다.

## 실제 결과

로컬 PostgreSQL 테스트에서 초안 비신호·공개/중단 신호·찜 삭제 신호·본인만 조회·수정 권한 차단·계정 삭제를 확인했다. hook 테스트에서 연속 변경 합치기·재연결/online 재조회·계정 구독 제거·저장 중 변경 후 재조회를 확인했다. 실제 Supabase WebSocket 전달·JWT 재인증·두 브라우저 지연 측정은 아직 확인하지 않았다. W25/W12 완료는 그 결과를 기록한 뒤 판단한다.

되돌릴 때 클라이언트를 기존 버전으로 복귀하고 publication에서 두 신호 테이블을 제거한다. 트리거·함수·신호 테이블은 별도 후속 마이그레이션으로 제거한다. 사용자 찜·저장·공연 원본 데이터는 지우지 않는다.

## 실제 연결 사용자 확인 · 2026-10-07

사용자가 수집 설정·실행·검수와 두 브라우저 실시간/계정 저장/복귀 검증을 포함한 안내 1~4를 모두 완료했고 문제가 없다고 보고했다. 이는 사용자 확인 결과이며 원격에서 에이전트가 재측정한 결과는 아니다. 수동 수집 업로드·화면 반영의 기본 연결은 확인한 것으로 기록한다. 정기 실행 반복 성공·마지막 성공 관측과 갱신 지연 수치는 추가 기록이 필요하다.

PR [#8](https://github.com/yeonguk0201/Concert_finder/pull/8)은 dev에 병합되었고 CI·Vercel 검사가 성공했다. 확인 시 원격 main은 이전 PR #7 버전이어서 main 통합과 실제 검증한 배포 커밋/브랜치는 별도 확인한다. 이전 적용 대기·404 기록은 당시 상태다.
