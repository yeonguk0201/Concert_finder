# W28 아티스트 DB 편집·노출 정책

2026-10-13 KST. 로컬 구현과 연결된 Concert_finder DB 마이그레이션 적용, 로그인된 localhost 관리자 화면 검증을 완료했다. 프런트 운영 배포·push·PR·병합은 수행하지 않았다.

## 구현 범위

- 관리자에서 이름·ISO 2자리 국가 코드·국내 록/해외 록/J-pop/미분류·별칭을 수정한다. 국가와 대상 분류는 별도로 저장한다. 이름·별칭·국가 검색과 상태 필터를 제공한다.
- 미검수·승인·보류·제외와 제외 후 복구를 지원한다. 변경 이유는 필수이며 승인은 분류·외부 식별자·HTTPS 공식 근거가 필요하다. 외부 신원이 장르 근거를 대신하지 않는다.
- 보류·제외는 일반 DB 목록에서 숨기고 외부 신원별 자동 공개 승인을 해제한다. 수집 후보의 신원 연결은 유지하되 자동 공개를 차단한다. 기존 승인 API와 공개 가져오기 API도 보류·제외 상태를 우회하지 못한다. 복구만으로 이전 승인이 되살아나지 않는다.
- 기존 band ID·공연 연결·찜·저장 일정은 보존한다. 기존 공개 공연을 일괄 철회하거나 이미 저장된 예매 알림을 해제하는 기능은 아니다.
- 모든 아티스트 행 등록/변경을 private 이력에 기록한다. 관리자 UI에서 선택한 아티스트의 최근 50건, 변경 전후 값·관리자 ID/서버 작업·KST 시각을 확인한다. 사진 변경도 같은 이력을 사용한다.
- 버전이 다르면 덮어쓰기를 거부한다. 저장 실패 시 입력을 유지하고, 성공 뒤 최신 목록이 도착하기 전에는 다시 저장할 수 없다. 이력 조회 실패는 재시도할 수 있다.
- 공개 RPC는 SECURITY INVOKER이며 private 구현에서 관리자 권한을 검사한다. 일반 역할의 bands 직접 쓰기를 해제했고, 관련 서버 전용 RPC 실행권한도 축소했다.

**W31 경계:** 현재 미검수와 승인 항목은 일반 DB 목록에 표시한다. 승인 항목만 검색하는 변경과 공개 외부 검색 패널 제거는 W31에서 진행한다. 기존 54팀을 일괄 승인하거나 장르 검수를 완료한 작업이 아니다. 사진 파일 업로드는 W30에 남아 있다.

## 적용·검증

[`20261013070742_artist_curation.sql`](../supabase/migrations/20261013070742_artist_curation.sql)을 공식 CLI로 생성하고 PGlite에서 검증한 뒤 실제 연결 DB에 `artist_curation` 마이그레이션으로 적용했다. 적용 전후 아티스트 54팀·공연 8개·찜 3개·저장 일정 5개·자동 공개 승인 0개다. 4개 출처의 자동 공개는 비활성 상태를 유지했다.

- Node 57개·UI 78개, 총 135개 회귀 검사 통과. RPC를 private 구현으로 정리한 뒤 관련 DB 검사를 재실행해 통과했다. 최종 UI 수정 후 17개 파일의 UI 전체 검사도 통과했다.
- lint·build·`git diff --check` 통과. 기존 500kB 초과 번들 경고는 유지한다. 최초 샌드박스 UI 실행은 임시 파일 ENOENT로 실패했고 일반 로컬 환경에서 다시 실행했다. 추가한 UI 검사의 필드셋 비활성 확인·복구 데이터·toggle 이벤트 모사를 수정한 후 통과했다.
- 실제 관리자 UI에서 Oasis 이름·별칭·분류를 임시 수정하고 보류→제외→미검수 복구를 저장했다. 일반 검색에서 임시 별칭 결과 0팀을 확인했다. 기존 Oasis 찜 1개·공연 연결 7개를 보존했다. 최종 이름 Oasis·GB·별칭 오아시스·미분류·미검수·사진 auto/미지정을 복구했다. 복구 이유와 3건의 검증 이력은 남는다.
- 실제 DB에서 anon/비관리자 authenticated 역할의 숨겨진 행 조회·직접 수정·관리 RPC·이력 조회 차단을 확인하고 롤백했다. 실제 다른 계정으로 로그인한 검사는 아니다.
- 실제 DB에서 Ado의 승인→제외→가져오기 거부·재수집 후 제외/단일 ID 유지·승인 제거를 한 트랜잭션에서 확인하고 전체 롤백했다. 이 검사의 근거 URL 입력은 기능 검사용이며 Ado의 운영 장르 승인을 수행한 기록이 아니다. 실제 자동 공개 성공/복구는 로컬 DB 테스트로 확인했다.
- 320·390·1280px에서 관리자 입력 폼과 실제 데이터를 확인했다. 320px에서 기존 body 최소 너비가 세로 스크롤바 폭만큼 가로 넘침을 유발해 수정했다. 최종 `scrollWidth/clientWidth`는 각각 305/305·375/375·1265/1265px이다. 검증 탭의 관측된 콘솔 오류·경고 0건, 임시 viewport는 복구했다.

## 배포 대기·제약

`artist-search`의 보류·제외 전용 409 안내 응답과 공개 행 재확인 코드는 로컬 구현·검사만 완료했다. 원격 배포는 자동 승인 검토가 공개 JWT 검증 비활성 함수의 별도 배포 권한이 명확하지 않다는 이유로 거절했다. 우회 배포하지 않았다. 사용자의 명시적 함수 배포 승인 후 진행한다. 현재 배포 함수에서도 새 DB 정책이 가져오기를 거부하므로 재등록은 차단되지만 기존의 일반 실패 안내가 표시될 수 있다. 프런트 운영 배포도 별도다.

security advisor 비교에서 anon SECURITY DEFINER 실행권한 WARN 항목은 27→24개, authenticated 항목은 27→25개로 감소했다. 새 공개 RPC에 대한 추가 경고는 없다. 기존 다른 함수 실행권한 경고, private 스키마 정책 없는 RLS INFO 13개, 유출 비밀번호 보호 비활성화 WARN은 남아 있다. 전체 보안 하드닝 완료로 표시하지 않는다. [실행권한 점검](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable) · [비밀번호 보호](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

## 10/13 운영 출시 진행

사용자가 운영 배포·확인·로드맵 최신화와 PR 생성·main 병합을 명시적으로 요청했다. 위 배포 대기 기록은 이전 상태다. `artist-search` v8 ACTIVE 배포 후 원격 소스의 공개 행 재확인·409 분기와 로컬 파일 일치를 확인했다. 실제 HTTP 공개 Ado 검색 200, 무인증 가져오기 401 `LOGIN_REQUIRED`, 짧은 검색 400 `INVALID_QUERY`를 확인했다. 기존 JWT 설정과 함수 내부 사용자 인증을 유지했다.

출시 전 재검증: Node 57개·UI 78개(135개), 가져오기 도구 18개, lint·build·diff 검사 통과. UI 검사의 Windows 샌드박스 임시 파일 ENOENT는 일반 로컬 환경에서 재실행해 해결했다. 기존 500kB 초과 번들 경고는 남는다.

현재 DB 재조회: 아티스트 545팀(미검수 539·제외 6), 공연 8개. 대량 등록 후 543개 검수 보고서의 유지 533·제외 4·판단 보류 6은 DB 승인/보류 상태와 다르다. 네 출처 모두 `publication_enabled=false`다. 이번 출시는 자동 공개 활성화·가상 공연 정리·W30/W31 완료를 포함하지 않는다. 프런트 PR·main 배포 및 운영 UI 확인 결과는 후속 기록한다.
