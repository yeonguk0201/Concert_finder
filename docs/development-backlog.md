## 4. 완료 기록 방식

각 작업을 마칠 때 다음을 기록한다.

- 작업 ID와 구현한 사용자 동작.
- 변경한 기능·데이터 구조와 선택 이유.
- 직접 실행한 검증 및 실제 결과. 미검증 항목은 구분한다.
- PR 링크와 병합 여부. PR 작성만으로 작업의 배포 완료를 표시하지 않는다.
- 남은 제약·다음 작업·변경된 일정.

10/6에 D00와 W01~W04를 구현하고 실제 연결·사용자 확인 및 자동 검증 결과를 기록했다. W05~W09는 준비/로컬 구현과 외부 연결 검증을 구분한다. 실제 알림 수신은 미검증이며 출시 체크리스트를 자동으로 완료 처리하지 않는다.

### 실제 프로젝트 연결 후 추가 확인

사용자가 신규 프로젝트의 마이그레이션·환경변수·Auth URL 설정을 완료했다고 알려 개발 서버를 재시작했다. 공개 키로 9개 테이블을 REST 조회해 HTTP 200, 앱의 공개 카탈로그 관계 조회 200, private 스키마 조회 406/PGRST106을 확인했다. 이메일 provider 활성화와 로그인 링크 요청 성공도 확인했다. 목록은 현재 비어 있고 운영 DB에 가상 테스트 데이터를 넣지 않았다.

이후 사용자가 실제 이메일 링크 로그인과 로그아웃 성공을 확인했고 첨부 화면에서도 계정 로그인 표시를 확인했다. 로그인 후 새로고침해도 로그인 상태가 유지됨도 사용자가 확인했다. 만료/사용한 링크 처리·다른 기기 로그인은 아직 미검증이다. 빈 계정 테이블의 조회 결과만으로 원격 행 격리를 입증하지 않으므로 W02~W04 상태는 진행으로 유지한다. 연결 요청에는 기존 공개용 키만 사용했으며 비밀값·이메일 주소·토큰·첨부 원본은 기록하지 않는다.

### W03 오류 안내 보완

사용자 검증에서 발견한 만료/재사용 링크 안내 누락을 StrictMode effect 재실행으로 재현하고 수정했다(`3dd218c`). callback 오류를 초기 상태에서 읽고 query·fragment·동일 페이지 hash 이동을 처리한다. 데스크톱·390px 모바일에서 모의 otp_expired 안내를 확인했다.

로그아웃 후 재요청 실패는 실제 Supabase가 반환한 429/over_email_send_rate_limit으로 확인했다. 이메일 총량 한도·짧은 재요청 간격·요청량 제한·네트워크·서버 오류를 구분해 표시한다. 실제 발송 한도 안내와 총 17개 자동 테스트, lint/build를 검증했다. 제한 해제 또는 SMTP 준비 후 정상 새 링크 발송과 실제 만료/재사용 링크를 재검증한다. 상세 절차는 [로그인 오류 점검](backend-setup.md)에 기록했다.

이후 사용자가 SMTP 설정을 조정하고 만료/재사용 링크의 오류 안내와 새 링크 요청 후 정상 로그인 복구가 모두 동작한다고 확인했다. W03의 기본 로그인·로그아웃·새로고침 유지·오류 복구는 사용자 검증을 마쳤다. 다른 기기 로그인은 별도로 남는다. W01 초기 스키마 검증은 완료했지만 W02의 실제 A/B 데이터 격리와 일반 계정의 관리자 변경 차단은 아직 미검증이므로 완료로 표시하지 않는다.
