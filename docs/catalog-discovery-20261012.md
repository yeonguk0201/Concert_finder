# 공연 발견 범위·아티스트 자동 식별 보강

2026-10-12 KST. 10/11 W21 작업의 후속 보강이며 매시간 실행·자동 공개(W26/W27) 완료 기록은 아니다.

## 바뀐 동작

- 수집 전에 아티스트 8팀을 등록해야 하는 제한을 제거했다. ualive의 미등록 출연진도 공연 후보에 보존한다. 기존 8팀은 확인된 이름·프로필의 빠른 연결용으로만 사용한다.
- YES24 해외뮤지션 목록과 콘서트 메인에서 공연 링크를 발견하고, 상세 페이지의 공개 JSON-LD에서 한국 공연일·공연장·출연진을 추출한다. J-LIVE 달력은 연결된 YES24 링크 발견에만 사용한다. 제3자 사이트의 일정·가격·이미지·소개를 복사하지 않는다.
- `https://ticket.yes24.com/English/Perf/ID`도 `/Perf/ID`로 정규화한다. 출연진의 문자열·배열 형식을 모두 지원하며 다른 호스트·잘못된 날짜·한국 공연장이 아닌 결과는 거부한다.
- 공연 종료일이 오늘(KST)보다 이른 후보는 기본 수집에서 제외한다. 여러 날의 공연은 종료일까지 유지한다. `--include-past`로 과거 자료를 포함할 수 있다. 발표일이 오래됐다는 이유로 공연 날짜를 추측하지 않는다.
- 관리자 후보 기본 화면은 **예정 공연**이다. **날짜 미확인 / 지난 공연 / 전체**를 선택할 수 있고 각 건수를 보여준다. 이전 업로드의 과거 후보를 DB에서 삭제하지 않는다.
- 미등록 출연진은 MusicBrainz 이름·별칭 검색으로 보완한다. 정확히 대응하는 결과가 하나이고 국적이 확인되며 검색 결과가 잘리지 않은 경우, 외부 MBID로 자동 등록·연결한다. 검색 실패·동명이인·국적 미확인은 이름과 이유를 남겨 검수한다. 기존 동명 아티스트를 근거 없이 합치지 않는다.
- 관리자 **아티스트 검색·가져오기**에서 공연이 없는 아티스트도 찾고 선택할 수 있다. 검색은 등록하지 않으며, 가져오기는 해당 MBID를 서버에서 다시 조회한다. 같은 ID는 기존 등록을 재사용한다. 가져온 이름·별칭은 일반 검색과 찜 목록에 반영된다.
- 일반 사용자 검색은 저장된 카탈로그와 외부 아티스트를 함께 찾는다. 계정 모드에서 두 글자 이상 입력하고 400ms 동안 입력이 멈추면 MusicBrainz 이름·별칭 검색을 요청한다. 방문자는 로그인 없이 결과를 볼 수 있고, 로그인한 일반 사용자도 국적·소개로 대상을 선택해 고유 ID로 등록하고 찜할 수 있다. 로컬 프리뷰에서는 외부 검색을 요청하지 않는다.
- MusicBrainz 신원 정보는 공연 개최나 대상 장르의 공식 검증을 대신하지 않는다. 새 아티스트의 장르는 `장르 미검수`로 표시하고 공연은 검수 후보로만 저장한다. 초기 채움은 `initial_import: true`를 유지한다.

## 적용 순서

기존 `202610110001_catalog_expansion.sql`, `202610110002_concert_artwork.sql`을 이미 적용했다면 아래 새 파일만 추가 적용한다. 기존 두 파일을 다시 실행하지 않는다.

1. Supabase Dashboard → SQL Editor → 새 쿼리에서 [`20261011150237_discovered_artist_catalog.sql`](../supabase/migrations/20261011150237_discovered_artist_catalog.sql)의 전체 내용을 실행한다. YES24 후보 URL, 출연진 연결, 외부 검색 캐시·공유 요청 제한·서버 전용 등록 RPC를 추가한다.
2. 프로젝트 폴더의 PowerShell에서 Edge Function을 배포한다. `YOUR_PROJECT_REF`는 Supabase 프로젝트 URL `https://YOUR_PROJECT_REF.supabase.co`의 프로젝트 ID다. CLI 로그인이 필요하면 `npx supabase login`을 먼저 실행한다.

   ```powershell
   npx supabase functions deploy artist-search --project-ref YOUR_PROJECT_REF
   ```

   함수의 Supabase 기본 서버 환경변수를 사용한다. 별도 MusicBrainz API 키는 필요하지 않다. `service_role` 키는 브라우저용 `VITE_` 변수에 넣지 않는다.

3. 앞서 사용한 서버 업로드 환경변수가 설정된 같은 PowerShell에서 수집·업로드한다.

   ```powershell
   node scripts/collect-catalog.mjs --output=collection-report.local --upload
   ```

   YES24만 다시 수집하려면 `--source=yes24`를 추가한다. 외부 아티스트 제공처가 혼잡해 공연 수집부터 진행하려면 `--skip-artist-lookup`을 추가한다. 이 경우 이름을 보존하되 새 외부 ID는 조회하지 않는다.

4. 새 프런트엔드를 실행하거나 기존 프로젝트 배포 절차로 반영한다. 관리자에서 **예정 공연**을 검수하고, 미연결 이름은 **아티스트 검색·가져오기**로 보완한다. 기존에 같은 공연을 등록했다면 기존 공연을 수정하고 공식 출처를 추가해 중복 공개하지 않는다.

이 작업에서는 원격 SQL·Edge Function·프런트엔드를 배포하지 않았고 DB에 후보를 업로드하지 않았다. 기존 두 SQL의 적용과 이전 후보 공개는 사용자 실행 보고에 근거한다.

## 조회 제한과 남은 범위

- MusicBrainz 조회는 의미 있는 User-Agent와 요청 간 1.1초 제한을 적용한다. 수집기는 성공 결과를 `.artist-cache.local`에 7일 캐시하고 즉시 저장한다. 실행당 새 조회 25회, 요청당 5초, 연속 실패 2회 이후에는 추가 조회를 보류한다. 보류된 이름은 다음 실행에서 보완할 수 있다.
- 검색 Edge Function은 DB의 단일 요청 게이트로 인스턴스 간 요청을 제한하고, 성공 결과를 7일 캐시한다. 검색은 공개이며, 가져오기는 Auth `getUser`로 검증한 로그인 사용자에게 허용한다. 등록할 이름·국적은 클라이언트 값을 신뢰하지 않고 선택한 MBID로 서버에서 조회한다. 서버 전용 RPC는 일반 계정에 허용하지 않는다.
- 외부 검색과 수집기를 동시에 대량 실행하지 않는다. MusicBrainz 공개 API의 비상업 이용은 무료이며 상업적 이용 전에는 제공처 조건·요금제를 확인해야 한다. [API 문서](https://musicbrainz.org/doc/MusicBrainz_API).
- `--output` 보고서는 출처 완료마다 중간 저장한다. 실행 중에는 `complete: false`, 모든 출처 처리가 끝나면 `true`다. 출처 실패 여부는 각 `error`/`failures`로 따로 확인한다. 터미널에는 출처 시작·후보 수·완료를 표시한다.
- YES24 `robots.txt`는 HTTP 200의 HTML 오류 페이지였다. 이를 정상 robots 지침으로 주장하지 않으며 보고서 `warnings`에 기록한다. 로그인·예매 실행·비공개 API는 사용하지 않는다. J-LIVE robots는 공개 달력을 허용하고 관리자 페이지는 제외한다.
- YES24 신규 경로는 포스터를 가져오지 않는다. 일반 예매 오픈 시각도 `offers.validFrom`만으로 확정하지 않으며, 공식 발표일·공연 형식·대상 장르는 관리자 확인 대상이다.
- NOL·Ticketlink 목록·Live Nation의 동적 목록, 전체 목록 페이지 넘김, 투어 전용 페이지의 도시별 일정, 출처 간 자동 중복 통합은 아직 미지원이다. J-LIVE에서 발견해도 NOL 링크만 있는 공연은 이번 경로로 가져오지 않는다.

## 수집·관리자 검색 구현 검증

- 전체 Node 테스트 43개와 UI 테스트 56개 통과. 마지막 변경 뒤 수집/SQL/외부 검색 10개와 관리자 UI 9개를 다시 확인했다.
- lint, TypeScript·Vite build, Deno `check supabase/functions/artist-search/index.ts` 통과. 기존 500kB 초과 번들 경고는 남아 있다.
- PGlite에서 실제 마이그레이션 실행, 미등록 후보 보존, MBID 재등록 중복 방지, 연결 수정 번호, 초기 채움·공개 없음, 공유 요청 제한, 캐시 갱신, 일반 계정의 서버 RPC 접근 거부를 확인했다. 원격 DB advisory 검사는 수행하지 않았다.
- 실제 관리자 컴포넌트를 가상 백엔드와 연결한 브라우저에서 1280px·390px의 날짜 필터·검색 결과와 가로 넘침 없음을 확인했다. 원격 배포 이후의 관리자 검색→실제 DB 등록은 아직 미검증이다.

## 일반 사용자 외부 검색·찜 후속 구현

- 일반 검색에 국적·유형·소개·별칭·MusicBrainz 정보 링크를 표시한다. 공연이 없어도 선택한 MBID로 등록한 아티스트를 계정에 찜한다. 등록 결과를 즉시 카탈로그에 추가해 찜 목록에서도 표시한다.
- 검색만으로 아티스트나 공연을 생성하지 않는다. 같은 MBID는 기존 ID를 재사용한다. 기존 동명 아티스트와 연결 근거가 부족하거나 국적이 없으면 자동 등록을 보류하고 이유를 표시한다. 다른 신원을 이름만으로 합치지 않는다.
- 검색어·계정 변경 중 늦은 응답은 무시한다. 검색 제공처 혼잡은 다시 검색할 수 있고, 등록 뒤 찜 저장이 실패하면 기존 ID로 재시도할 수 있다. 찜은 공연 알림 예약을 의미하지 않는다.
- 새 DB 마이그레이션은 없다. 위 적용 순서의 기존 SQL이 적용돼 있어야 한다. 변경된 `artist-search` 함수를 먼저 배포하고 프런트엔드를 배포한다. 기존 함수는 관리자만 허용하고 새 화면에 필요한 `band` 행을 반환하지 않으므로 함수와 화면을 함께 갱신해야 한다.
- `npm test`: Node 44개, UI 63개 통과. 일반 사용자 검색→등록→찜, 공연 없는 ID의 DB 찜 보존, 방문자 로그인 유도, 동명 검색 결과 선택, 오래된 응답·계정 변경, 저장 실패 재시도를 검증했다.
- lint·build·diff 검사 통과. 기존 500kB 초과 번들 경고는 남아 있다. 가상 백엔드와 실제 컴포넌트를 연결한 headless Edge에서 1280·390·320px 선택·찜과 가로 넘침 없음, 페이지 오류 없음을 확인했다.
- 이번 후속 변경은 로컬 검증까지 완료했다. 원격 함수/화면 배포와 실제 제공처→운영 DB 등록·찜 검증, Deno 런타임 검사는 수행하지 않았다. 공개 검색은 공유 게이트에서 혼잡 응답을 받을 수 있다.

## 검색 결과 품질·응답 개선

- 이름·별칭 필드와 국적이 있는 Person/Group만 제공처에서 검색한다. 서버에서도 국적 미확인·유형 미확인·Other 등의 항목을 제외하고, 이름 정확 일치→별칭 정확 일치→긴 검색어의 단어 구문 일치→단일 긴 검색어의 접두 일치 순으로 최대 10개를 표시한다. 3자 이하의 짧은 검색어는 이름·별칭 정확 일치만 허용한다. 이름만으로 동명이인을 합치거나 인기·공식 신원을 판정하지 않는다.
- 새 `query:v2:` 캐시 키로 이전의 넓은 검색 캐시를 재사용하지 않는다. 캐시를 읽은 결과에도 서버 필터를 적용한다. 같은 화면에서 반복하는 외부 검색은 정규화한 검색어별로 5분간 최대 20개를 브라우저 메모리에 보관한다. 실패 응답은 캐시하지 않는다.
- 입력 대기는 600ms에서 400ms로 줄였다. MusicBrainz 자체 응답 시간·공유 요청 제한·혼잡을 제거하는 변경은 아니다. 실제 공개 API 확인에서 Ado 첫 요청은 503이었고 후속 요청은 약 925ms, green apple은 약 323ms였다. Ado 일본 가수가 첫 결과, Mrs. GREEN APPLE이 해당 검색의 첫 결과로 남음을 확인했다. 전체 서비스의 응답 시간 측정이나 속도 보장은 아니다.
- 반영하려면 `artist-search` 함수를 다시 배포해야 한다. 로컬 프런트엔드 변경만으로 운영 함수의 필터가 바뀌지는 않는다.
