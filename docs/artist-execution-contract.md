# 아티스트 실행 역할과 ID 계약

2026-10-30 사용자 요청에 따른 현재 계약이다. 과거 실행 기록의 포괄적인 ‘새 ID 생성 금지’와 역할 설명은 아래 구분으로 해석한다. 이 문서는 운영 등록을 지금 실행하라는 지시가 아니다. 현재 단계는 **prepare**이며 다음 사용자 재개 지시까지 등록·승인·queue 쓰기를 실행하지 않는다.

## 내부 행 ID와 외부 신원 ID

| 필드 | 의미와 생성 규칙 |
| --- | --- |
| `bandId` / `bands.id` | 우리 DB 새 행의 내부 UUID. 검증한 신규 아티스트를 지원 경로로 등록할 때 표준 UUID 생성기로 한 번 할당할 수 있다. 원래 고정 목록과 불변 journal에 같은 값을 기록하고 재시작/재시도에도 재사용한다. 등록/중복/수동보호 거절을 피하려고 다른 ID로 바꾸지 않는다. |
| `musicBrainzId` / `bands.musicbrainz_id` | 실제 제공처의 외부 아티스트 신원. 공식 신원·국가·동일 원작/관계와 대조한 기존 canonical ID만 사용한다. 임의 UUID 생성, 이름 추정, 내부 행 번호 복사로 누락을 채우지 않는다. |
| `runId` | 정상 배치 실행 식별자. 실제 아티스트 신원이나 등록 완료의 증거가 아니다. |

내부 UUID 할당은 신원 검증·운영 승인·DB 등록이 아니다. 신규 등록에 필요한 정확한 외부 신원/국가/동일 별칭 근거가 없으면 계속 미완료다. 내부 ID도 현재 catalog·외부key·별칭 충돌 검사와 같은 최대40팀/5시간 임대·원본버전·수동 결정·receipt/공개검색 검증을 통과해야 한다. 새 writer, 임의 INSERT, service import/seed 우회는 허용하지 않는다. 기존 readyToApply=false·자동 검토 거절 입력과 원문 checkedAt은 그대로 보존한다.

요네즈의 기존 pending `bandId=0d2368ee-72d7-4ec8-aa52-5a708452963f`와 canonical MBID `09d4a85c-4916-4b4e-bc96-c4cfcf371046`는 서로 다른 네임스페이스다. 이번 작업에서 새운영ID를 만들거나 기존입력/상태를 바꾸지 않는다. 실제 등록 재개 시 최신 catalog와 같은 pending 입력을 다시 검증하고, 종료된 과거run/저널/명령을 재전송하지 않는다.

## 실행 역할과 현재 단계

- `artist`: 아티스트 조사·등록·별칭·분류·승인·채널의 담당 역할이다. 운영 실행이 재개된 단계에서만 기존 지원 명령을 `--role=artist --owner=cloud`로 사용한다. `owner`는 local/cloud 인계 소유권이며 역할과 별개다.
- `monitor`: 공연 운영 SELECT·비식별 집계·공개 준비 readback·로컬 감시 기록만 담당한다. 미등록 아티스트의 필요 요건은 기록하되 아티스트 업무를 대신 실행하지 않는다.
- `prepare`: 현재 작업 단계다. 역할 지침과 호환 코드·격리 테스트를 준비한다. **artist 역할이라는 이유로 prepare 단계에서 begin/checkpoint/apply/identity/finish를 실행하지 않는다.** 검증 통과나 시간이 지난 사실만으로 운영 실행 단계로 전환하지 않는다.

queue CLI는 역할 미지정 시 monitor로 취급한다. monitor에는 기존 state의 `status` 읽기만 허용하며 환경 파일 로딩·디렉터리/lock 생성·RPC 없이 읽는다. `snapshot`도 artist queue에 파일을 쓰므로 artist 역할을 명시해야 한다. `context`는 내부에서 서버 배치 등록을 수행할 수 있으므로 monitor에서 금지한다. `init/accept/handoff`의 CLI 지원은 이번 복구 상태에서 실행할 권한이 아니다.

```sh
# 기존 queue 읽기만: 현재 준비/감시 단계에서 사용 가능
node scripts/artist-review-queue.mjs status --role=monitor --owner=cloud
```

`--role=artist`는 실수 방지용 실행 의도 표시이며 인증·권한 부여·자동 승인 검토의 우회 수단이 아니다. Supabase 서비스 인증, 실제 사용자 범위, 서버 임대·원본 버전·수동 결정 검사는 계속 필요하다. 직접 라이브러리 호출이나 다른 writer로 이 경계를 우회하지 않는다.

## 예약과 채팅 이력

현재 아티스트 예약 `6adb621bc36881919e076b05944350a6`과 감시 예약 `6adb6225f7288191899b0476085114e5`는 역할별 지시문을 가진다. 예약의 현재 `EXECUTION_ROLE`과 `EXECUTION_PHASE`를 해당 실행의 범위로 확인한다. 과거 다른 역할의 요청을 현재 역할의 쓰기 권한이나 전역 금지로 전용하지 않는다. 최신 사용자의 구체적인 단계/금지는 그대로 따른다.

두 예약이 같은 thread에 연결돼 있다는 사실은 별도로 남긴다. 현재 예약 수정 도구에는 thread/conversation 변경 필드가 없어 물리적인 채팅 분리를 수행하거나 완료로 주장할 수 없다. 새 예약 복제·수동 실행·중지된 이전 예약 활성화로 대신하지 않는다. 역할별 prompt·CLI 검사는 충돌 예방 조치이며 자동 승인 검토의 미래 판단까지 보장하지 않는다.

공연 수집 예약 `6ad9f566088c8191a029db4fd20b5613`, 기존 서버 수집/발송 워커, 중지된 이전 두 예약의 지시·일정·활성은 이 작업에서 변경하지 않는다. 다른 환경에 파일이 자동 전달됐다고 가정하지 않는다.

## 다음 단계의 콘텐츠 범위

개인 포트폴리오는 허용된 공식 API의 공연 사실정보와 출처 링크를 우선한다. 외부 기사/공지 본문·포스터/사진/이미지를 수집·전재·다운로드·영구 재업로드하는 작업은 제외한다. 필요한 최소 사실 요약·출처/확인 시각과 원문 전재는 구분한다. 기존 보존 근거/사진 캐시를 이번 작업에서 지우거나 다시 갱신하지 않는다.

등록 차단과 출처별 실제 이용 범위 해결은 이 분리 단계 뒤에 진행한다. 자료 출처와 예매 링크 목적지를 구분하는 NOL 검사 보완, 공개 실행기/무알림 초기 공개 최종 검증은 후속 작업이며 현재 차단 로직/공개 OFF를 바꾸지 않는다. 공개ON·운영DDL·배포·push/PR/merge·실제 발송은 별도 범위다.
