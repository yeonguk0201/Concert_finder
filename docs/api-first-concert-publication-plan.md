# AI 없이 동작하는 API 중심 공연 자동 공개 계획

현재 배포·최초 실제 공개·공개 목록 정리 및 남은 정기 트리거 확인은 [2026-11-10 로컬 UI·중복 작업 인계](release/local-ui-and-concert-dedup-handoff.md)를 먼저 참조한다. 아래는 최초 작성 시점의 계획/운영 제한 기록이며 현재 설치 상태를 대신하지 않는다.

작성: 2026-11-09 KST. 이 문서는 사용자와 합의한 목표와 다음 구현 방향을 인계한다. 이번 요청에서는 문서만 작성하며 수집 실행·운영 DB 변경·배포·예약 활성화는 하지 않는다.

## 사용자가 원하는 결과

정해진 시간마다 일반 서버 코드가 공식 API를 호출하고, 코드 검증을 통과한 공연을 사이트에 무알림 자동 등록한다. 정상 실행에 ChatGPT 예약, AI 검색·추론·검수, AI가 매번 작성하는 검수 계획 파일이 필요해서는 안 된다. 요네즈 한 건의 성공이나 스케줄 enabled/CI 성공만으로 완료라고 하지 않는다.

AI는 개발과 예외 조사에 사용할 수 있다. 예외 조사 없이도 정상 공연은 계속 등록되어야 하며, API에 없는 정보를 AI가 매번 찾아 채우는 것을 정상 경로로 만들지 않는다. 공연별 공개 승인을 반복해서 요구하는 구조도 목표가 아니다.

## 현재 상태와 오래 걸린 원인

기존 KOPIS 수집기, source lease/중복 방지, 검수 사실 보존, 무알림 공개 RPC와 연속 공개 준비 경로가 있다. 하지만 현재 경로는 사람이 검수한 fresh review plan에 의존하고, 최초 발표일·일반예매 시각·외부 공지 이용 근거까지 공연 공개의 필수 요건으로 요구한다. KOPIS에 없는 필드를 외부 공지에서 AI로 조사하면서 완전 무인 운영을 달성하지 못했다.

2026-11-09 인계 시점의 기존 예약은 사용량 절약을 위해 사용자가 의도적으로 중지한 상태다. 장애나 자동화 미완료의 원인으로 혼동하지 말고 명시적인 재개 요청 없이 켜지 않는다.

직전 검수는 기존 batch `2026-11-08T16-25-04-224233Z`의 고정14건이다. 모두 현재 KOPIS와 대조했고18개 회차를 로컬 정규화했지만 전체 공개 검수 통과0이다. 조용필 서울의 공식 발표일·예매 시각과 이무진 고양의 공연장 예매 시각 등 일부 근거를 추가했다. 준비 자료를 DB 사실 반영이나 실제 공개 receipt로 세지 않는다.

위 두 검수 기록은 원래 클라우드 작업 브랜치에만 있고 계획 문서 공유 PR에는 포함하지 않는다. 다른 환경에 없을 수 있으므로 이 문서의 상태 요약을 인계 기준으로 삼되, 실제 운영 값은 작업 시 다시 읽는다. `docs/continuous-concert-publication.md`도 원래 런타임 checkout에는 없었으므로 다른 환경의 설치 상태를 자동 전달된 것으로 보지 않는다.

## 목표 구조

기존의 단일 일반 스케줄러 → KOPIS API → 정규화 → 결정적인 검증 코드 → 기존 지원 RPC로 저장/공개 → 공개 읽기 및 알림0 확인.

현재 ChatGPT 예약에만 실행 진입점이 있는지 먼저 확인한다. 목표는 AI가 없는 일반 스케줄러다. 기존 GitHub workflow 등 실제 사용 가능한 실행 주체 하나를 선택하고 중복 실행 소유권을 정리한다. 이 문서만으로 새 예약/서버 스케줄러를 만들거나, 중지된 작업을 켜거나, 배포하지 않는다.

신규 제공처 연결보다 우선할 일은 공개 기준과 기존 서버·클라이언트 검증·UI를 같은 계약으로 맞추는 것이다. 기존 파일을 구버전/main 전체로 교체하지 말고 실제 후속과 최소 변경을 비교한다.

## 제안하는 공개 계약 — 아직 운영 적용하지 않음

공연 사실과 예매 사실을 구분한다. 필드가 없다는 이유로 값을 날조하거나 기존 verified 값을 일괄 true로 바꾸지 않는다.

| 항목 | 제안하는 처리 |
|---|---|
| 공식 API의 안정적인 공연 ID·출처 | 필수. KOPIS 식별자와 URL, 실제 관측 시각, 적용 이용 조건 보존 |
| 제목·대상 장르·국가·장소·공연 날짜 | 필수. 누락·모순은 해당 후보만 보류 |
| 회차 | 명시적인 날짜·시각 또는 모호하지 않은 요일 안내를 코드로 정규화. 상품 기간을 매일 회차로 추정하지 않음 |
| 출연진 | 실제 출연진과 기존 승인 신원 연결 검사. 대표 한 명으로 전체 출연진 승인을 대신하지 않음. 미등록/모호한 연결만 기존 아티스트 담당에게 보완 요청 |
| 최초 발표일/발표 시각 | API에 없으면 null/미확인. 공개 필수 요건에서 분리하는 것이 이번 계획의 핵심 변경 |
| 일반예매 시작 시각 | 허용된 공식 API에서 확인할 때만 표시. 없으면 null/미확인으로 공연 자체는 공개 가능하게 변경 |
| 예매 목적지 | 출처별 허용 경로만 사용. 미허가 상품 딥링크는 제외하고 공연 정보 공개와 분리 |
| 중복·수동 차단·취소·중요 변경 | 계속 보호. 같은 출처/공연 식별자를 우선하며 비슷한 제목/날짜만으로 병합하지 않음 |

발표일·예매 시각을 선택 항목으로 만드는 것은 현재 운영 계약을 변경하는 설계다. 현재 서버가 필수로 검사하는 조건을 env, 직접 SQL writer, 가짜 근거로 우회하지 않는다. 필요한 migration/검증/정규 릴리스는 해당 작업의 실제 승인 범위 안에서 진행한다. 이 문서는 그 운영 변경이 완료됐다는 증거가 아니다.

회차가 API에서도 모호한 경우는 자동 공개 범위에서 보류하는 것을 기본안으로 한다. 날짜만 있는 공연을 별도 공개 유형으로 지원할지는 구현 시 명확히 결정하고 시간 미확인 표시를 검증한다. 시각을 임의로 만들지 않는다.

## 다음 구현 순서

1. 현재 원래 checkout·코드·체크포인트·서버 계약·기존 스케줄러 소유권을 읽어 확인한다. 새 checkout/reset/queue 재생성으로 대체하지 않는다.
2. KOPIS 응답만으로 필수 공연 사실을 정규화하는 검증기를 만든다. 원본 수집과 기존 사실 보존 guard를 유지하고, 사람이 작성한 fresh review plan 없이 통과 여부를 결정한다.
3. 서버 공개 검증과 저장 계약에서 최초 발표일/예매 시각을 선택 항목으로 분리한다. 아티스트 승인·수동 차단·중복·동시성·기존 검수 사실 보호는 유지한다. 변경된 계약과 검토한 executor digest를 명시적으로 맞춘다.
4. UI에서 ‘발표일 미확인’, ‘예매 시작 시각 미확인’을 실제 null 상태에 맞게 표시한다. 게시일/수정일·자정 timestamp를 만들어 채우지 않는다.
5. 일반 스케줄러 하나에서 수집부터 무알림 공개까지 연결한다. 기존 source lease·최근 실행·cooldown을 공유하고, 다른 KOPIS 정규 수집과 중복되지 않게 한다. AI 실행 파일이나 AI 검수 계획이 없어도 정상 동작해야 한다.
6. 격리 검증·lint/build 후 승인된 정규 릴리스 경로로 반영한다. 실제 한 회차와 그다음 정규 회차를 관측해 아래 완료 기준을 충족하는지 확인한다. 사용자가 중지한 예약을 검증 명목으로 재개하지 않는다.

범위를 다시 외부 공지14건 완전 조사로 되돌리지 않는다. 새로운 예매 API는 후속 선택 기능이며 기본 공연 자동 공개의 선행 조건이 아니다. 기존 상세 근거는 버리지 않고 선택 정보를 채우는 데 사용한다.

## 다른 채팅/로컬에서 이어가기

파일은 이 checkout에 존재하며 같은 경로의 문자열만으로 다른 채팅/클라우드 인스턴스와 공유된다고 보장할 수 없다. 로컬 커밋도 push 전에는 원격 저장소에 없다. 이어받는 채팅은 실제 파일과 git commit을 확인해야 한다. `.local` ignored 상태와 secret binding은 Git 문서와 별개이며 자동 복사되지 않는다.

다른 환경에서 이 문서가 보이지 않으면 사용자가 이 Markdown을 전달하거나, 승인된 Git 전달 절차를 사용한다. 작성 이후 사용자가 이 계획 문서와 AGENTS.md의 원격 공유 및 main 대상 PR 생성을 요청했다. PR 생성과 실제 병합은 구분하며, 병합 후 사용자 PC에서는 해당 브랜치를 pull해야 한다. 문서 공유는 수집 실행·운영 변경·예약 재개의 승인이 아니다.
