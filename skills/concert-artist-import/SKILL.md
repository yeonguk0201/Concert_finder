# 아티스트 대량 추가

J-pop 솔로·그룹과 록 밴드를 확충한다. 이번 스킬의 록 기본 범위는 **밴드(Group)**이며 록 솔로까지 확대하지 않는다. 일본 국적이나 밴드 형식만으로 장르를 인정하지 않는다.

## 실행 범위

- 스킬 생성·설치와 API 질문만으로 실제 DB 추가를 실행하지 않는다. 사용자가 “아티스트 추가해줘”, “이 스킬로 DB 확충해줘”라고 요청하면 해당 범위의 수집·추가까지 진행하며 항목마다 다시 묻지 않는다. 미리보기 요청은 파일 수집만 한다.
- 수량 미지정 시 최대 500개 신규 후보를 목표로 수집한다. 확보량은 태그와 기존 등록 상황에 따라 적을 수 있다. 전 세계 전체/인기순/누락 없는 목록으로 설명하지 않는다.
- 기본 소스는 MusicBrainz. 태그는 **후보 선별용 보조 근거**이며 공식 장르 검증이나 공개 승인으로 취급하지 않는다. 자동 분류·승인·제외는 이 스킬에서 하지 않는다. 검수까지 요청되면 별도 `concert-artist-curation`을 적용한다.
- 신규 등록은 `unreviewed`, `unclassified` 기본값을 사용한다. 현재 앱은 미검수도 표시하므로 DB 추가 요청 범위를 알릴 때 이 점을 설명한다. 검증된 항목만 추가하라는 요청이면 수집 파일에서 먼저 공식 근거를 검증한 ID만 선별한 뒤 가져온다.

## 토큰을 적게 쓰는 실행

1. 저장소의 AGENTS.md/CONTRIBUTING.md와 [DB 및 실행 참조](references/operations.md)를 읽고 대상 프로젝트·실행 권한을 확인한다. DB 작업 시 Supabase 스킬을 따른다.
2. 번들 `scripts/import-artists.mjs`를 Node 22 이상으로 실행한다. API JSON 전체를 채팅/도구 출력에 넣지 않고 UTF-8 파일로 직접 저장한다. 모델에는 집계, 오류 코드, 필요한 소수 사례만 전달한다.
3. `collect`는 태그별 페이지를 순회하고 외부 ID로 합치며 페이지마다 체크포인트를 저장한다. 같은 파일로 재실행하면 이어서 수집한다. 목록이 부족하면 기존 후보 전체를 다시 읽거나 재검색하지 말고 `--limit`을 늘린다.
4. 실제 추가 요청이 있으면 `import --apply`로 실행한다. 숨김 상태까지 포함한 DB 스냅샷으로 기존 MBID를 건너뛰고 기존 `service_import_artist` RPC만 사용한다. 동일 이름 충돌은 DB 판단에 맡겨 보류하며 이름만으로 병합하지 않는다. 읽기 확인 실패나 권한 오류 때 쓰기를 중단하고 결과를 보존한다.
5. 스크립트 결과의 실제 처리 수를 보고한다. 수집 수, 기존 등록 건너뜀, 등록/재사용 확인, 신원 충돌, 보류/제외 차단, 실패를 구분하고 결과 파일을 링크한다. RPC 반환만으로 신규 등록 수라고 주장하지 않는다.

기존 이름·별칭·국가·검수 상태·사진을 덮어쓰거나 보류/제외를 복원하지 않는다. 공연·찜·일정·알림에는 쓰지 않는다. 사진은 수집하지 않는다. 수집 기록은 저장소 커밋 지침을 따르되 키나 임시 대량 응답은 커밋하지 않는다.

## 소스 이용

- [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API): 의미 있는 User-Agent, 앱 전체 초당 1회 이하. DB 인증 환경이 있으면 기존 공유 요청 게이트를 사용한다. 인증 없는 수집은 검색 UI나 다른 수집기와 동시에 실행하지 않는다.
- [검색 필드](https://musicbrainz.org/doc/MusicBrainz_API/Search): `tag`, `type`, 페이지 offset 사용. 태그 누락은 비대상 근거가 아니다.
- [이용·데이터 조건](https://musicbrainz.org/doc/About/Data_License): 핵심 데이터와 부가 데이터의 조건이 다르며 비상업적 API 사용은 무료다. 상업 이용·태그 재배포 전에 최신 조건을 확인한다. 태그는 후보 파일에 보조 근거로 보관하고 DB 장르에는 `장르 미검수`만 기록한다.
