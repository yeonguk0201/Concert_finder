# 아티스트 대량 추가

J-pop 솔로·그룹과 록 밴드를 확충한다. 이번 스킬의 록 기본 범위는 **밴드(Group)**이며 록 솔로까지 확대하지 않는다. 일본 국적이나 밴드 형식만으로 장르를 인정하지 않는다.

## 실행 범위

- 스킬 생성·설치와 API 질문만으로 실제 DB 추가를 실행하지 않는다. 사용자가 “아티스트 추가해줘”, “이 스킬로 DB 확충해줘”라고 요청하면 해당 범위의 수집·추가까지 진행하며 항목마다 다시 묻지 않는다. 미리보기 요청은 파일 수집만 한다.
- 수량 미지정 시 최대 500개 신규 후보를 목표로 선발한다. 기존 등록분은 재정렬·삭제하거나 지표/사진을 덮어쓰지 않는다. 신규 수집부터 유명도 우선 정책을 적용한다.
- 기본 유명도는 **Last.fm 청취자 수(listeners)**다. 더 넓은 후보 풀에서 J-pop과 록을 각각 정렬하고 기본 50:50으로 선발한다(요청 비율이 있으면 우선). 한 범위가 부족하면 다른 범위의 유효 지표 후보로 채운다. 양쪽 태그가 있는 항목은 J-pop에 배정해 중복 선발을 막는다. 이는 후보 풀 안에서 Last.fm 이용자 기준의 순위이며 한국/일본 현지 인기·최근 인기·전 세계 상위 목록을 보장하지 않는다.
- Last.fm 키가 없으면 원본 수집까지 진행하고 `LASTFM_API_KEY` 연결이 필요함을 알린다. 오류·동명·지표 누락을 0점으로 바꾸거나 MusicBrainz 검색 점수/태그 수로 대체해 인기순이라고 보고하지 않는다. 비순위 등록은 사용자가 명시적으로 요청한 경우에만 `--allow-unranked`로 실행한다.
- 기본 소스는 MusicBrainz. 태그는 **후보 선별용 보조 근거**이며 공식 장르 검증이나 공개 승인으로 취급하지 않는다. 자동 분류·승인·제외는 이 스킬에서 하지 않는다. 검수까지 요청되면 별도 `concert-artist-curation`을 적용한다.
- 신규 등록은 `unreviewed`, `unclassified` 기본값을 사용한다. 현재 앱은 미검수도 표시하므로 DB 추가 요청 범위를 알릴 때 이 점을 설명한다. 검증된 항목만 추가하라는 요청이면 수집 파일에서 먼저 공식 근거를 검증한 ID만 선별한 뒤 가져온다.

## 토큰을 적게 쓰는 실행

1. 저장소의 AGENTS.md/CONTRIBUTING.md와 [DB 및 실행 참조](references/operations.md)를 읽고 대상 프로젝트·실행 권한을 확인한다. DB 작업 시 Supabase 스킬을 따른다.
2. 번들 `scripts/import-artists.mjs`를 Node 22 이상으로 실행한다. API JSON 전체를 채팅/도구 출력에 넣지 않고 UTF-8 파일로 직접 저장한다. 모델에는 집계, 오류 코드, 필요한 소수 사례만 전달한다.
3. `collect`로 목표의 기본 5배(500개 목표면 2,500개) 후보 풀을 모은다. 태그별 페이지 순회·외부 ID 중복 제거·체크포인트로 이어받는다. 풀의 수집 순서에는 인기 의미가 없다. 이미 존재하는 파일의 범위를 줄여 목표 수라고 가장하지 않는다.
4. `scripts/prepare-artists.mjs`로 기존 등록·보류·제외 MBID를 제외하고 Last.fm 지표를 가져와 선발한다. 7일 캐시를 재사용하고 실패는 다음 실행에 재시도한다. 입력 풀과 준비 출력 파일을 분리한다. 선발된 항목만 MusicBrainz URL 관계를 읽어 공식 사이트·Spotify·YouTube·Instagram·X 링크 후보를 확보한다.
5. 실제 추가 요청이 있으면 준비 파일로 `import --apply`를 실행한다. 기본 실행은 7일 이내의 유효한 순위 지표가 없으면 DB 쓰기 전에 거부한다. 숨김 상태까지 포함한 DB 스냅샷과 기존 `service_import_artist` RPC로 중복/제외를 보호한다. 동일 이름 충돌은 DB 판단에 맡기며 읽기 확인 실패나 권한 오류 때 쓰기를 중단한다.
6. 수집 풀 크기·유효 지표 수·범주별 선발 수·미확인/실패 수와 실제 등록 결과를 구분해 보고한다. 목표 미달은 실제 수와 이유를 알리고 임의 비순위 항목으로 채우지 않는다. RPC 반환만으로 신규 등록 수라고 주장하지 않는다.

## 프로필 정보와 이미지

- 링크는 MBID의 URL 관계에서 확보하고 조회한 신원의 ID를 대조한다. 자동 결과는 `identity_linked_unverified`다. 공식 사이트/소속사 소개의 교차 링크 등을 확인한 뒤 `verified`와 근거 URL·확인일을 기록한다. 팬 계정·Topic/자동 생성 채널·동명이인은 공식으로 승격하지 않는다. 공식 여부 미확인만으로 아티스트 등록을 막지는 않는다.
- 짧은 소개는 확인한 공식 소개를 사실 위주로 요약하고 원본 URL·확인일을 보관한다. LLM 기억으로 생성하거나 Last.fm biography를 복사하지 않는다. 근거가 없으면 비워 둔다. 장르 태그로 검증된 소개를 만들지 않는다.
- 인기 지표·프로필 링크·소개 근거는 준비 파일/캐시에 보관한다. 현재 등록 RPC에는 해당 저장 필드가 없으므로 DB에 저장됐다고 보고하거나 `description`에 억지로 넣지 않는다. 향후 상세 페이지용 스키마·쓰기 경로는 별도 구현한다.
- 이미지 확보는 별도 단계다. 출처 표시 없는 목록 UI를 목표로, 무표기 사용 허락이 확인된 공식 홍보 사진·CC0/퍼블릭 도메인을 우선 검토한다. 다른 이미지의 크레딧 위치는 실제 이용 조건에 맞춘다. 플랫폼 공식 링크가 있다는 이유로 사진 표시 조건이 충족됐다고 간주하지 않는다.
- YouTube/Spotify 프로필 사진을 자동 크롤링·다운로드하거나 기존 사진을 교체하지 않는다. 추후 API 사용 시 공식 계정 확인과 표시·링크·브랜딩·갱신 조건을 검토한다. 사진이 없으면 이니셜을 유지하며 사진 확보 때문에 등록을 지연하지 않는다.

기존 이름·별칭·국가·검수 상태·사진을 덮어쓰거나 보류/제외를 복원하지 않는다. 공연·찜·일정·알림에는 쓰지 않는다. 사진은 수집하지 않는다. 수집 기록은 저장소 커밋 지침을 따르되 키나 임시 대량 응답은 커밋하지 않는다.

## 소스 이용

- [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API): 의미 있는 User-Agent, 앱 전체 초당 1회 이하. DB 인증 환경이 있으면 기존 공유 요청 게이트를 사용한다. 인증 없는 수집은 검색 UI나 다른 수집기와 동시에 실행하지 않는다.
- [검색 필드](https://musicbrainz.org/doc/MusicBrainz_API/Search): `tag`, `type`, 페이지 offset 사용. 태그 누락은 비대상 근거가 아니다.
- [이용·데이터 조건](https://musicbrainz.org/doc/About/Data_License): 핵심 데이터와 부가 데이터의 조건이 다르며 비상업적 API 사용은 무료다. 상업 이용·태그 재배포 전에 최신 조건을 확인한다. 태그는 후보 파일에 보조 근거로 보관하고 DB 장르에는 `장르 미검수`만 기록한다.
- [Last.fm artist.getInfo](https://www.last.fm/api/show/artist.getInfo): MBID와 API 키로 청취자 수 조회. 응답 MBID가 일치해야 지표를 연결한다. [tag.getTopArtists](https://www.last.fm/api/show/tag.getTopArtists)는 태그 수 순서이므로 청취자 인기순으로 취급하지 않는다. [API 이용 조건](https://www.last.fm/api/tos)은 상업 이용 전에 확인한다. Spotify deprecated popularity나 YouTube 지표 조합 점수를 대체 지표로 만들지 않는다.
